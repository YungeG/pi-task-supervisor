# Supervisor 日志膨胀与恢复开销修复方案

状态：**修复方案已通过独立 subagent 复审（OK）；未批准实施。**

本文交付诊断、修复范围和验收合同，不代表源码已经修改。审阅通过、性能目标或 READY 均不构成实施、提交、推送、安装、迁移真实日志或重载会话的授权。

## 1. 目标与分析基线

优先解决 **Supervisor 为什么重复写入大量数据**，随后降低既有大历史的恢复成本，不以减少真实证据或放松安全校验换取性能。

- 仓库基线：`5aa8b71a6b877e105ed1ce70864ca4c1ff71a006`（main）。
- 实测安装包：R5 / 源码 `7814a2a`，内容寻址包 SHA-256 `52b83558fe850bf0899d6fca7b3221045ef7464924c9885e7d0c2632193becd8`。
- main 合入了日志错误诊断和界面改进，但仍保留本文涉及的重复物理扫描链路。安装包与 main 不是同一版本，实施后必须重新验证，不能沿用旧测量声称通过。
- 基准 L1：本机真实会话的只读取样；不将真实工具参数、输出、凭据或会话文件纳入仓库。
- 本文源代码定位以符号为准，不将旧文档的行号或旧候选状态当作当前实现事实。

## 3. 根因

### 3.1 v1 将不可变事实、可变状态和展示摘要整体持久化

旧状态包含累积 receipts。新增一条回执或改变控制状态时，将此前回执一起重新追加，形成：

```text
状态1 + 回执1
状态2 + 回执1、2
状态3 + 回执1、2、3
...
```

在固定单条大小、每条结果生成一次增长快照的条件下，累计正文接近二次方增长。500 条数组上限限制的是单次状态，不是追加日志总字节；L1 有 9 份包含全部 500 条回执的快照，合计约 9.76 MB。

### 3.2 当前新格式已处理新增回执，但不会消除旧物理数据

`saveSupervisor` 在 ReceiptStore 存在时保存 v2/v3 小检查点；新账本追加独立回执并使用有界正文缓存。新 GoalRun 的检查点还可能包装在 v5 `goal-state` 内。

同时，无 store 的旧格式兼容路径仍可保存完整状态。不能因兼容路径存在就宣称当前 v3 正常路径仍二次方增长，也不能因新格式存在就宣称旧文件已变小。

特别注意：`startSupervisor` 的运行时 state 仍使用 version 1 结构，但正常持久化可为 v3。**必须检查实际持久化记录及账本关系，不能只看运行时 version 字段做格式守卫。**

### 3.3 恢复层重复承担同一份物理日志检查

L1 的稳定只读恢复依次经过：

1. `events.ts:restoreSession` 的初始 `inspectRestorableSession`；
2. `restoreGoalLifecycle -> readGoalJournal`；
3. `restoreBoardHuman`；
4. `restorePreflight -> readPreflightFold`。

每条路径都可能独立扫描、解析、摘要计算和重建祖先关系。`human-journal.ts:parseEntry` 对输入记录计算摘要；只减少 retainedData 不会省掉之前的完整解析和摘要计算。

这些工作同步执行，阻塞扩展恢复及其所处的事件循环。对话 compact 缩小模型上下文，不等于缩小这里读取的物理日志。

### 3.4 性能验收粒度不够

当前 `human-journal.test.ts` 的性能用例是 100 节点、最多 64 KiB 的单次 inspect，存储资源测试主要验证新格式路径。它们不能代替“旧格式重负载下完整 session_start 的扫描预算和物理字节预算”。

## 4. 不变条件与本轮排除项

必须保留宿主证据身份、审查/因果版本、绑定、退出码要求、GoalRun/分支隔离、人工授权闭包、未知执行结果屏障、显式恢复与不自动重放的语义。

本轮不做：

- 新数据库、持久索引、全局长期缓存、后台归档进程或新的账本 wire 版本；
- 截断/删除/重编号真实历史，重算旧证据身份，迁移正在使用的真实 session；
- 增加任务/续跑预算，缩短受保护证据，降低日志或 schema 安全检查；
- 将所有回执改为只存原生 ID；本轮允许每条事实保留一份既有的有界脱敏摘录；
- 通用“相同 payload 就不写”的拦截器，避免破坏需要真实 append/parent 确认的证明闭包。

## 5. 阶段 A：先验收新增写入不会再次膨胀

### A1. 审计所有生产者，而非重写现有 ReceiptStore

覆盖启动、tool_call/tool_result、重复结果、暂停、恢复、停止、审查、最终验收与连续 GoalRun 切换。为每个调用登记：事实记录、控制检查点、视图读取、旧格式兼容或安全屏障。

- 每个唯一宿主结果在其账本作用域内最多保存一条 receipt；intent、close_unknown 等独立语义记录不算重复 receipt，仍必须存在。
- 新目标必须建立 ReceiptStore，后续丢失账本不能静默退回“完整 receipts 状态”。
- 控制检查点只携带控制状态、bindings、账本头和原有作用域信息，不重新嵌入历史回执正文。
- 状态查询、界面刷新和重复处理同一已记录宿主结果不得附带全量保存。
- 先验证当前实现；满足合同的路径只补回归，不为凑写集重构。

### A2. 明确旧格式兼容责任

- v1 历史继续可读，状态查看不迁移、不重写。
- 显式 recover 继续遵循原有迁移、暂停、授权、预算和 freshness 规则。
- `retainLegacyGap` 等必要安全写入保留其幂等屏障及物理 append 确认，不能为减小体积而删除。
- 若增加“禁止回退”的检查，必须区分真实旧来源和新格式运行态，不以 runtime.version 或目标文字猜测身份。

主要符号：`supervisor.ts:startSupervisor/saveSupervisor/observeTool/retainLegacyGap`，`receipt-store.ts:prepareToolCapture/commitToolReceipt/appendCheckpoint/checkpoint`，`events.ts` 的宿主事件处理与 `runtime.ts` 的实例状态。

完成条件：当前新路径的字节增长、旧路径兼容和失败守卫有测试证明；不承诺在没有新事实的情况下给所有状态转换强行去重。

## 6. 阶段 B：统一同一次只读恢复的日志检查

由 `restoreSession` 编排一次已验证、只读的 SessionJournal，将其显式传给内部恢复投影；不让每个投影自行创建相同检查。

建议改动位置：

| 位置                                                                                    | 职责                                                       |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `events.ts:restoreSession`                                                              | 拥有恢复读取周期、验证与失效顺序                           |
| `human-control.ts` / `human-journal.ts`                                                 | 提供检查结果和来源身份；保持严格 reader                    |
| `goal-lifecycle.ts` / `goal-journal.ts`                                                 | 只读投影可复用 supplied journal；提交路径保持新鲜证明      |
| `board-human.ts:restoreBoardHuman`                                                      | 从同一已验证快照恢复回应，派生状态不修改快照节点           |
| `preflight.ts:readPreflightFold/restorePreflight`                                       | 同周期读取，不跨阶段复用授权判断                           |
| `supervisor.ts:readSupervisorHistory`                                                   | v5 历史中的重复 `readGoalJournal` 也接入同一只读周期       |
| `preflight.ts:confirmedPreflightProof/verifiedPreflightProjection/readPreflightStartup` | 区分恢复投影与实时授权用途；恢复只读链路显式传递受限快照   |
| `supervisor.ts:startupContext/readSupervisorStartRecord`                                | 从共享日志派生严格祖先前缀，不向启动校验暴露未来或兄弟记录 |

### B1. 快照有效范围

- 仅限一次内部、只读恢复周期，绑定实际 session、leaf、生命周期 epoch、文件身份和观察到的文件元数据。
- 分支/会话替换、文件变化及恢复期间追加均使它失效；在接受投影前检查来源新鲜度。
- 采用有界重读；连续变化无法取得稳定视图时保持阻止执行并报告，不能无限阻塞或默认成功。
- 对**已有持久日志**，即使内存里没有 owner 记录，也至少做一次真实磁盘/祖先检查，不能用内存缺失绕过检查。合法无文件例外见 B4，不将其强行转成磁盘日志。
- 元数据检查不是恶意文件系统并发改写的 OS 隔离保证，不改变原有摘要语义或谎称获得原子事务。

### B1a. 恢复自身的 epoch 变化采用显式交接

`restoreSession` 进入时会使旧回调失效；其后 `restoreGoalLifecycle -> installGoalView` 即使不写磁盘，也会再次调用 `invalidateGoalCallbacks()`、递增 `goalEpoch`。这是已确认的内部行为，不等于文件或外部目标发生变化。

本方案选择**受控的同步 epoch 交接**，不忽略 epoch，也不依靠重试重复安装：

1. 完成恢复入口原有的取消/失效动作后，建立私有恢复读取帧，保存 runtime、manager、session/leaf、文件来源及 `expectedGoalEpoch`。
2. 只读 fold 使用已验证日志；在本轮编排直接拥有的 `installGoalView` 同步安装步骤之前，检查当前 epoch 等于帧的预期值，且未发生 B2 的追加。
3. 在这个不跨 await 的安装步骤前后，验证同一 runtime/manager/session/leaf/文件来源；有目标视图安装时只接受该步骤**确定的一次** epoch 递增，无视图安装时接受零次。额外递增或其他身份变化一律使帧失效，不能通过读回当前 epoch 无条件“更新缓存”来放行。
4. 安装符合预期后，仅推进该帧供后续**只读恢复投影**使用的 expected epoch。旧 planning lease、人类回调与所有授权/执行能力仍按原逻辑失效，不能因读取快照续用而复活。
5. 外部取消、会话/树切换、其他异步阶段变化均不属于交接；按原失效路径丢弃。若目标切换需要提交，先走 B2 新鲜证明及写后确认，再建立新的读取帧。

交接仅存在于内部恢复编排，不开放工具参数或通用“允许 epoch 变化”选项。补充稳定 v5 GoalRun 的一次扫描测试，以及安装前、安装后、await 间隙发生额外 epoch/身份变化的拒绝测试，避免只用没有目标安装的 L1 样本证明合同。

### B2. 写入必须结束原读取周期

恢复并非永远只读：`restoreGoalLifecycle -> commitPending` 可提交已确认的切换；旧容量缺口和部分 hold 路径也可能追加。

这些路径须保留执行前的新鲜证明和 append 后的物理确认。只读快照不得用于替代这些检查；写入后重新建立读取周期，再继续投影。

**一次扫描预算只适用于已有持久日志、稳定且无写入的恢复。** B1a 的受控投影安装不重复扫描；合法恢复写入所需的额外检查必须保留并单独计量，不能为了达标将其删掉。

### B3. 深层消费者与严格历史前缀

不能只改外层四个入口。符号级实施包须覆盖 `readSupervisorHistory -> readGoalJournal` 及 preflight fold 内的 `confirmedPreflightProof`、`verifiedPreflightProjection`、`readPreflightStartup`、`readSupervisorStartRecord` 等深层只读路径，计量整个 session_start 的物理读取，而非仅顶层函数。

启动校验原有的 `startupContext` 使用截止指定 entry 的祖先前缀。共享读取必须从同一已验证快照派生该前缀，并同时限制 branch、nodes 查找集合和可见 leaf；**不能只裁剪 branch，却让 nodes 仍能查询未来或兄弟记录**。前缀内的 owner/GoalRun、审批和启动关系继续按既有历史规则校验，不能借完整日志中的后续 witness/commit/receipt 闭合此前的证明。

这些复用入口仅供内部只读恢复投影。实时授权提交、实际启动/执行、追加观察确认仍从原来的新鲜物理检查路径进入，不接受模型提供的 journal、路径或前缀来绕过准入。

### B4. 保留合法无文件例外

严格保留 `inspectRestorableSession` 的既有行为：

- 显式内存会话（没有 session 文件路径）：零次物理读取，不因此获得新的可恢复授权证明。
- 尚未创建文件且 `getEntries()` 没有任何 `type === "message"` 的 setup-only 会话：零次物理读取，不为了凑一次扫描而创建或修复文件。
- 文件路径不存在但已有 message，或文件无法读取：继续 `JOURNAL_UNAVAILABLE`，不能归类为上述例外。
- 文件已经存在：即使没有 owner/会话消息，也必须进行一次严格物理检查；例外不授权跳过真实文件。

## 7. 阶段 C：旧历史治理单独决策

A/B 不会缩小 L1 的 352 MiB 文件。第一轮接受一次严格物理扫描，不触碰原始记录。

若后续仍需缩小，另行设计离线迁移，明确旧 ID、parent、legacyBase、binding、control/witness、未闭合 intent 和所有可达分支的兼容规则。迁移必须有独立副本、回退路径及用户授权，不能作为本轮隐藏动作。普通 `/compact` 或只保留最后快照都不是替代方案。

| R9  | 显式内存会话和无 message 的缺文件 setup-only 会话分别为零次物理读取；缺文件且有 message 拒绝；已有文件无 owner 仍严格检查                                                                                              |
| G1  | 原有功能、负向授权/恢复测试和覆盖率门保持通过，不降低阈值、放宽 wire 或绕过校验                                                                                                                                        |

W3 的计量对象是 Supervisor 新增持久数据，不包括 Pi 原生 transcript；500 条旧容量屏障本身和迁移边界另用 W2 验证，不能把旧目标直接扩成 1000 条。大样本前先冒烟，禁止直接以全量历史发现导入/配置错误。

性能目标是 L1 稳定只读恢复由约 14.7 秒降至预期 4–6 秒，属于待验证目标，不是硬件无关保证，更不是完整 reload 的承诺。扫描次数/新增字节/语义一致性是优先的确定性验收，耗时采用同机前后对比。
