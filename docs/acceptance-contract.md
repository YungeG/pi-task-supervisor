# Local candidate: source-bound acceptance contracts

This is an uncommitted local candidate, not an installed release, an OS sandbox, real human/product acceptance or an independent definition-quality review.

## Construction and separate authority

1. During native preflight or an active Goal, Main can call `propose_contract({proposal})`. The host supplies the actual Session/preflight-or-original-Goal source reference. Proposals are untrusted metadata: no model-supplied owner, trust flag, command result or permission is accepted.
2. Existing native permission approval and independent first-start remain mandatory. Once a real owner exists, `/task-supervisor review-contract <proposalId>` requires idle Main, resolved controls/executions and an uncompiled/draft board. It presents the original Goal, complete conditions, checker/configuration/invocation/environment/scope, captured version and invalidation effects.
3. Only the actual native opaque response plus matching physical witness can bind `native-reviewed` authority. This neither grants business permission nor starts/resumes Main. RPC/ordinary SDK UI DTOs and copied answers are unsupported. A separately recognized fixed host specification can instead bind `recognized-host`; that is not relabeled native confirmation.
4. A normal preflight-backed Goal cannot compile, claim, advance, use workflow gates or run registered checks before binding. Ordinary tools retain their independent existing permission/owner/late-result rules; the contract gate is not another business authorization system. Explicit legacy/already-compiled no-contract history stays legacy, never silently upgraded.

Technical revisions require a new explicit native review and preserve requirement meaning/source and controlled scope. Important requirement/scope changes require a new Goal/preflight and appropriate authorization. Binding/revision is currently restricted to before first compilation; replacing a checker cannot silently reuse old observations.

## Actual automatic checks

`run_check({checkId})` resolves only the current bound automatic definition. Main cannot supply its executable, script, argv, cwd, environment, result parser, requirement mapping or trust source.

The initial capability is **Linux / Node v25.9.0**, a finite benign fixed Node checker with exact script/argv/cwd, captured checker/configuration bytes and explicit nonsecret environment. Native Node permission flags restrict file reads to captured paths and grant no filesystem writes, child processes, workers or addons. This is **not a hostile-code sandbox or network/business authorization**; checker quality and actual allowed effects still require independent review. Arbitrary Bash/shell, remote/background or writing checkers are not upgraded by their names or a claimed exit code.

The process must actually close. Cancellation, timeout or kill acknowledgement is not close proof. The host retains actual PID/termination/exit, bounded output digest, before/after byte versions and observable file generations; copied execution DTOs cannot enter its private original-result registry.

The checker prints exactly one JSON object:

```json
{"protocol":"check-result-v1","tests":1,"passed":1,"failed":0,"skipped":0,"requiredCases":{"declared-case":"passed"},"skippedIds":[]}
```

Counts must be safe nonnegative integers with consistent totals, at least the declared minimum and a positive passed count. Failed, zero, malformed, required/disallowed/all-skipped results cannot pass. Genuine exit zero remains recorded even when this policy rejects it; it is never substituted for semantic success.

The separate semantic gate requires every mandatory condition to have a successful applicable trusted observation, with exact contract/definition/invocation/environment/checker/version/generation/source identity. It uses the newest causal observation rather than bypassing a later failure. Task all-done and a different successful/no-op check are insufficient.

Automatic qualification also requires the original actual host receipt/kernel end and current owner/mode/human frame. Nested checks require the P6 qualified quiet root. Later/overlapping potential writers, unqualified root/store/model/image effects and unknown results still block. Observable file timestamps alone are not proof against same-byte rewrites: native writer history/P6 barriers remain independent requirements.

## Manual conditions

`/task-supervisor verify-check <checkId>` asks the bound manual choice/information question using the existing private native-answer registry and physical control/witness. It shows original Goal, full relevant conditions/check meaning, scope/workspace and exact version/generation. The actual host workspace must match before questioning and remain unchanged during review.

A negative response is retained but does not pass. Information remains information, not permission. A new artifact version needs a new applicable response. Chat text, old business approval, SDK custom UI output or a copied response cannot create manual proof. This command does not advance tasks, grant permissions, first-start, resume Main or replenish budgets. An interrupted control/witness group remains held without replaying the question.

## History, limits and display

- New facts use `acceptance-contract-v1`; old readers lacking it must refuse. Existing P0 byte-version preimages and old native control/witness bytes are unchanged.
- An actual final-review start can bind selected contract/observations to the exact P3 board/bindings/epoch tuple; a later sealed accepted outcome preserves history. Cold restoration makes no provider/process call or current check frame. Its sealed-contract history reads share the existing source-checked restore cycle, preserving the one-full-scan budget; a later live applicability request still performs a fresh physical read. Historical acceptance is not fresh applicability.
- The older P3 exact retained Bash validation-only path is unchanged. This candidate does not expose a generic rerun or business-replay path for completed Goals through `run_check`; an unavailable supported revalidation path remains a hold, not an invented pass.
- Maximum16 requirements/checks,64KB complete proposal/human/review material,16KiB per native fact,8 distinct proposals per target,256 definition facts,128 automatic runs and128 manual controls per owner; the acceptance view separately caps the combined observations at128. Capacity is an explicit hold, not truncation/eviction of authority. Some complete material fits individual facts but still exceeds the review cap and is rejected before UI/append.
- Resident UI/review projections distinguish task records, host bindings, contract/model-review history, native manual-response records and unknown current applicability. They do not hash files, hydrate journals, dispatch providers/processes or adopt owners. Tasks mode never displays supervised/product acceptance.

## What the tests establish

Owned SDK/faux/QuickJS producers exercise actual top-level and only-mode checks, original receipts, missing required invocations, no-op substitution, malformed/zero/skip/nonzero results, late/parallel writers and sealed-history cold reading. Public native component/physical-adapter tests simulate argv/TTY/UI to test proposal/review/manual/private-registry boundaries. Negative raw/projection mutants are not native positive execution proof.

The original preflight SDK smoke preserves its two original host checks and adds a fixed **recognized-host** specification plus a real registered Node check. It explicitly reports `nativeContractReviewInThisArm:false`; it is not a real CLI/person or native-reviewed product-flow claim. The separate native proposal/review component tracer tests that source path. Actual real CLI/PTY/person/production acceptance remains unclaimed.
