## 1. 总体选择

推荐**在现有模块上分阶段收口**，不重写整套系统，也不引入新数据库或通用工作流框架。

- 只给 clear_execution 加一次查询、删掉 completed 恢复限制、截短所有正文，是最短补丁，但无法闭合状态、恢复、容量与证据新鲜度，且可能放开真实失效的验收。
- 全面替换日志与控制器会扩大兼容和恢复风险，没有必要。
- 推荐保留现有 owner、物理 control/witness、receipt ledger 和失败闭锁，把执行结算、最终审查、管理模式三个职责收口到现有模块的共同入口，再增加必要的版本化事实记录。

**目标行为**：普通工作可以明确不受任务管理；用户选择受管模式后，授权范围内连续推进。任务做完不等于目标接受；临时审查错误也不应要求重做所有任务。

## 2. 不可放松的不变量

1. 人工 pause/stop/revoke、未决授权、Session/GoalRun 身份失效优先；Advisor、Main 的字段操作或容器完成通知不能批准业务动作。
2. 未知执行结果保留现场，不回滚已写事实、不自动重放、不把 unknown 当 success。
3. 授权、首次启动、任务完成、目标验收是不同事实。退出管理不抹掉旧授权义务，也不终止外部进程。
4. 保留原始账本、已有 hash/preimage 和历史接受记录；新的摘要、资格确认和用量补记采用追加事实，不悄悄改写旧记录。
5. 只在真实关键写入确认后发布状态，持久化不确定继续闭锁；UI 失败不改变已经成功的业务结果。
6. H-01–H-09 已修复性质继续成立；不得重新引入重复恢复扫描、旧 v1 回落、终端控制串、未来阶段死锁或重复/重入 epoch 安装。
7. 现有安全负向回归和原覆盖率阈值不降低。行为策略确需改变时，显式替换相应旧行为断言，并保留其保护的权限、预算及失败性质。

## 3. 先分清状态，避免继续堆开关

以下是**拟议概念**，不是已经加入 CONTEXT.md 或协议的正式类型。

| 概念                         | 负责什么                                      | 不负责什么                               |
| ---------------------------- | --------------------------------------------- | ---------------------------------------- |
| 管理模式 ManagementMode      | 当前会话是否启用看板/监督                     | 不表示历史权限被清除或旧执行已结束       |
| 执行上下文 ExecutionContext  | 当前工具/回调属于哪个受管 GoalRun 或普通工作  | 不能由模型自填 Goal ID 或 parent ID 决定 |
| 执行结算 ExecutionSettlement | 外部 Run 的可信终态、结果处理和解除引用事实   | 不等于业务验证通过                       |
| 产物版本 ArtifactVersion     | 一次检查对应的已声明输入/产物、配置和环境版本 | 不是任意 OS/网络副作用的完整快照         |
| 最终审查 FinalReview         | 已完成工作是否可接受、是否需要重试/详情/重验  | 不重新批准权限、启动工作或重放执行       |
| 验收契约 AcceptanceContract  | 需求、检查定义、预期结果与适用产物的对应关系  | 不因有了 ID 标签就自动证明语义正确       |

管理模式、任务执行状态、最终审查状态分别记录和展示。建议区分“任务已完成／等待最终审查／审查可重试／需重新验证／已接受”，而不是把它们全部折叠为 board completed 或 fault。

最终持久化字段、版本号、旧状态投影和所有消费者须在实施前冻结；本方案不直接增加 wire5 枚举。

## 4. F-01：把执行引用的删除变成可信结算

**主要责任位置**：`async-execution.ts` 负责查询与结算规则，`tools.ts` 只请求状态转换并按现有持久化规则提交；最终验收检查结算记录。

### 推荐行为

1. bind_execution 记录宿主确定的 Session、GoalRun、执行器来源和 Run ID。执行标识不能因后续换目标而重新归属。
2. clear_execution 不再是无条件字段删除。它调用共同结算入口，取得新的执行器快照，核对 Session/Run/子节点，以及查询前后的 GoalRun、epoch、分支和绑定是否仍一致。
3. 返回明确的结果：
   - queued/running，或父 Run complete 但仍有 active child：保持引用和等待，不放行验收。
   - unknown、执行器不可达、快照过期/截断、身份不符：保持引用并显示待检查，不伪造终态。
   - 成功终态：追加终态观察和结果已处理事实，确认持久化后解除活动引用。
   - failed/cancelled 等终态：记录真实结果，允许结束“仍在运行”的等待，但保留未处理失败；按策略修复、重试或请求人工决定，不能自动标成功或放弃必需任务。
4. 终态观察和解除引用必须可追溯、幂等；追加结果不确定时不得只清内存字段。恢复要能识别半完成结算，不重跑外部工作。
5. 最终验收检查本目标所有已登记外部执行的结算，不只检查当前 executionRef 字段是否为空。

### 终态记录的必要内容

至少包括当前目标身份、Session/执行器来源/Run ID、所用协议、观察时间、终态及子节点摘要、执行器快照摘要、解除绑定事件和结果处理结论。若执行器不能保证 Run ID 不复用或终态不可回退，需要 generation/revision 或等价能力；在协议能力未确认前，不凭空生成这种保证。

本模块不擅自 kill/cancel 执行器，也不把“执行器报告终态”夸大为 OS 级永不再写证明。

**验收**：running 拒绝解除后仍不能接受目标；父 complete/子 running 保持阻塞；foreign/missing/stale/failed 明确处理；重复清理不重复副作用；写前/写后失败闭锁；重启后终态和未决处理不丢失。

## 5. F-04：调用用量与建议是否采纳分离

**主要责任位置**：模型适配器与 `supervisor.ts` 的调用/结果处理共同入口，不能仅交换两行后宣称覆盖所有错误路径。

- 每次真实 Advisor 尝试有唯一 call ID，绑定发起时的 GoalRun、模型、审查输入版本和尝试序号。
- 得到有效已知用量后，先按 call ID 记账，再处理 JSON/建议语义、引用、guide/next_batch 等是否可采纳。
- 已知用量仅记一次；同一 call 的重复交付须去重，冲突要可诊断。
- 请求失败、超时或取消后没有返回用量时标为 unknown/未结算；不能填 0 并当作已知零消费。
- 晚到响应归原调用，不能记到新 GoalRun。归档快照不改写；补记用量另行追加，历史视图区分归档时值和迟到补记，不安装旧运行态或恢复旧权限。
- 所有自动重试、动作纠正和详情轮次消耗真实调用预算；不因建议被拒绝而漏计，也不重置 reviews/continuations。

**验收**：合法但动作错误的 17 tokens/0.25 用例准确记账；解析拒绝、有用量的失败、取消/晚到、重复响应及跨 GoalRun 均不漏记、不重计、不串账。调用次数预算与金额/Token 统计分别断言。

## 6. F-02/F-03：最终审查与任务完成解耦

这两项应共同解决，避免“允许重试但数据包永远超限”或“数据包可处理但 completed 仍无法恢复”。

### 6.1 共同的有界审查视图

保留现有账本和宿主原始记录，改为生成独立审查视图：

- 必须完整保留目标/授权限制、验收条件标识、关键检查结论、适用产物版本以及可追溯的回执身份/hash。
- 工具输出正文、长任务材料及最近消息通过明确有界摘录/详情引用呈现；显示截断与遗漏，不能把摘录当作完整证据。
- 摘要中的退出码、检查计数、版本等来自宿主记录和受信解析器，不采用 Main 自写的“全部通过”替代事实。
- Advisor 当前无工具。建议增加受限的“需要哪些已登记证据详情”返回动作，由宿主补给只读内容；不开放任意文件、路径、执行或授权能力。详情轮次、单包字节和总时间/调用预算均有上限。
- 64,000 UTF-8 字节硬上限继续保留。即使缩短正文，必需元数据也可能超限；此时在编译/启动或完成提交前给出可操作错误，要求拆分计划/审查，不能静默省略必需条件。

同一个视图构造规则用于 done 前的候选可处理性检查和真实审查，不维护两套容量公式。写前检查先用候选看板与候选绑定构造，不先提交 done 再尝试检查。

### 6.2 只重试最终审查

建议增加独立的 retry-review 控制，而不是让通用 recover 绕过 completed 保护。

可重试必须同时满足：目标身份未变、权限仍有效、任务与绑定摘要一致、无未闭合执行/捕获、产物与验证前提仍为同一版本、证据资格有效。只重跑 Advisor，不重做任务、不重发授权/首次启动、不回滚已写事实。

推荐自动策略：临时 503/可重试传输错误至多一次自动重试，全部尝试共用原 30 秒期限及原调用预算；已经超时或预算不足则保持“最终审查待重试”，由人显式 retry-review，不要求重建目标。认证错误、上下文失效、证据缺失和容量错误不能套用网络重试。

发生产物变化时进入“需重新验证”，而不是继续使用旧证明。若目标尚未接受且范围未变，可在同一 GoalRun 收集新验证并重新终审，不重演已完成业务；范围或权限改变则走原有新授权/目标交接。已经 accepted 的历史接受事实不改写，另行表示当前版本是否仍有效。

**验收**：最终审查 503 后保持任务/证据并仅重试审查；真正修改产物则不能复用旧证明；16×1600 中文回执可通过有界视图处理且账本不变；不可处理的必需元数据在 done 前拒绝；详情缺失不能被当成通过；重试不复位预算、不绕过人工 hold。

## 7. L-01–L-04：明确可选管理模式与退出语义

### 7.1 推荐模式

| 模式       | 工作方式                                                       | 启动 Advisor | 普通工作是否自动归到旧 GoalRun |
| ---------- | -------------------------------------------------------------- | ------------ | ------------------------------ |
| off        | 普通聊天、编码、Git；任务变更工具不启用，保留只读历史/状态入口 | 否           | 否                             |
| tasks      | 显式轻量任务看板，按阶段续跑，不增加模型审查                   | 否           | 否；受管任务操作有自己的归属   |
| supervised | 显式选择的当前 GoalRun 内，执行权限/启动/证据和验收流程        | 是，按需     | 只归到宿主指定的当前执行上下文 |

推荐新会话默认 off；**不把已恢复的受管会话静默迁移为 off**。会话中的当前目标记录与当前执行上下文分开：历史已停止/已完成目标可读，但不能因此把整场后续对话永久挂在旧 GoalRun 下。tasks 模式的 done 只能表示看板记录完成，不能显示成与 supervised 的目标验收等价。

工具准入、上下文注入和结束续跑共同使用一个模式/归属决策入口，避免各处分别猜 enabled、Supervisor 状态与 GoalRun phase。模式、调用归属和父子身份由可信宿主确定，不接受模型参数自行退出管理或切换目标。

### 7.2 命令推荐语义

- enable：进入轻量 tasks 模式；只打开看板，不隐式启动 Advisor。
- supervise：明确进入 supervised 流程。新入口统一说明规划、权限确认和独立首次启动；不再因是否存在 legacy 历史而悄悄改变含义。兼容入口如需保留，单独标明，不自动走“新会话直接开始”的快捷路径。
- pause：留在当前管理上下文并暂停，保留所有真实门禁与计数。
- stop：立即取消自动监督/继续、结束当前目标；不表示外部进程已停止。
- disable：幂等请求退出会话任务管理，即使没有 Supervisor、只有看板也能使用；写入明确的持久化模式记录，而不是扫描“历史上任何 enabled=true”来决定状态。
- status：显示管理模式、当前执行归属、最后目标、阻塞原因、可执行的恢复/退出动作与已知加载修订；不知道加载版本时明确 unknown。

### 7.3 安全退出

stop 的“取消监督”动作不应因执行器未知而失效；但完整退管/释放受管执行上下文仍需确认宿主静止、回调租约失效、没有未知写入或未处理外部执行。

常见的已完成且静止场景中，stop/disable 后返回普通工作上下文，不再因旧 GoalRun phase 拦住新授权的 Git 操作。若仍有 running/unknown 执行，则显示 stopped-with-attention：自动监督已停，结算仍待处理，不宣称已经安全释放或验收。第一版不提供静默强制脱离；是否支持人工承担风险的另行脱离，须单独定义授权和持久语义。

退出不删除授权记录、不代替拒绝未决问题、不让旧 grant 变成新工作的许可。旧回调仍按旧归属隔离，不能成为当前进展或证据。宿主层卸载扩展和本命令的模式切换继续明确区分。

### 7.4 完成后的后续工作

- 只读查看使用可信只读工具，不因旧目标已完成而要求重建目标。
- 对潜在变更调用，不能靠解析 Bash 字符串就当成只读。可证明所有验收输入/产物和前提未变时，允许保留或重新确认当前版本有效性；否则要求新验证，不沿用旧证明。
- 产物版本至少覆盖已声明的源码/构建输入、相关配置/环境及必要的未跟踪输入；Git commit ID 不覆盖脏工作树。未声明或不可判断的外部副作用不能只靠文件 hash 消除风险。
- 用户原目标若包含提交/合并等交付步骤，应在契约中把这些列为验收前或明确的交付检查，不先宣布全部完成再强迫用户重建同一流程。
- 另行授权的独立后续工作可以在 off 下正常执行，或显式建立新受管目标；不复用旧 GoalRun 的权限、任务 ID、配额或证据身份。

**验收**：fresh/resume、legacy/scoped、无 Supervisor/active/stopped/completed 的模式矩阵；无未决事项时 stop 后可执行普通新工作；有未知执行时不能假退出或接受目标；恢复尊重最新持久模式；新消息、换目录不隐式转移目标；旧回调不串入新上下文；卸载/重载另行验证。

## 8. S-01/S-02：提高推进韧性，但不取消约束

### 8.1 进展不能只有任务状态，也不能只是工具次数

增加宿主可核验的 ProgressFact：例如契约检查由失败变通过、预定里程碑对应产物版本已形成、受管输入范围出现新的有效差异。

事实应绑定 GoalRun/任务/产物版本，去掉时间戳等噪声、去重并防止 A↔B 循环反复刷进度。Main 只能引用事实，不可单方面声明“有进展”。任务保持 implementing 时，只要存在新且适用的事实就不按状态停滞误暂停；总审查/继续预算和最长等待仍保留。

**验收**： implementing 多轮真实新里程碑不误暂停；重复读、相同成功输出、时间戳变化、反复切换相同差异仍不能无限续跑。

### 8.2 机械批次交接优先由宿主决定

真实前置门禁已满足、无已领取批次、存在 ready 任务、没有未结算执行且仍在已授权契约内时，宿主可生成确定性 next_batch，不必每次让模型再选择动作名称。语义审查仍在需要判断目标偏差或验收时运行。

过渡期间可对 guide/next_batch 的动作不匹配容许一次有预算的纠正，仍校验身份、引用和前置条件。重复错误转为可诊断阻塞；任何 hold、人工 pause/stop、授权缺口不得被改写成继续。所有已发生调用按第 5 节记账。

**验收**：就绪下一批不因一次动作名错误直接要求重建目标；hold 不被宿主覆盖；事实改变后不使用旧续跑决定；纠正次数、时间与费用可追踪且有界。

## 9. I-01：Code Mode 需要可信调用树与容器静止点

这是独立集成工作，不能通过给所有 codemode 加 readOnlyHint 修复。

### 9.1 需要的宿主事实

operation/root/parent 身份、真实开始/完成顺序、GoalRun 归属、叶子工具的效果分类、未结束子调用、检查对应的产物版本。正式修改文档已核对 SDK 1.1.0 的 parentToolCallId / executeTool：应先消费已有可信元数据，不默认要求新增宿主父子字段。缺失字段、非工具效果和具体插件实现仍要资格验证，不能从模型代码文本或自报 parent ID 猜测。

只有已证明不能直接产生未观测副作用、所有子调用均受宿主观察的容器，才可作为“编排容器”处理。否则仍按潜在变更/未知路径失败关闭。

### 9.2 新鲜度与完成提交

- 内层成功检查先记录为候选事实。容器/子调用未结束时，不允许目标最终接受。
- 容器静止后，根据真实顺序和适用产物版本判断检查之后是否发生相关修改；有晚写则失效，没有晚写才追加资格确认。旧 receipt 正文/hash 不改写。
- only 模式若在容器内请求 done，应返回明确的 deferred/not-done，并保存受宿主身份绑定的完成意图；不能假称已完成，也不能当场跳过 pending 屏障。
- root 正常结束且所有子调用已结算后，由宿主重新校验 GoalRun、人工门、任务摘要、产物/证据版本及完成意图，再执行一次原有持久化提交。中间出现 stop、换目标、晚写、容器失败/崩溃或结果未知，不自动提交，不重放工具。
- 双重结果/重复唤醒按 root/intent ID 幂等；没有宿主桥接时，明确报告能力不支持，不能把仅模拟的嵌套事件当成真实 only 模式验收。

**验收**：真实 Code Mode only 模式端到端；检查后无晚写可以在静止后完成，检查后再写必须重验；嵌套/并发子调用、暂停、错误、重启未知状态及伪造父子关系都不能误接受。

## 10. B-01：把验收提升为可追溯检查契约

建议将原有 preflight acceptance 文本发展为可执行对应关系，但不把模型贴标签当作证明：

`用户/规格中的条件 ID → 受信检查定义与预期 → 产物/输入版本 → 宿主执行回执 → 当前可接受结论`

- 条件有来源，不能只从 Main 自己列的任务反推“需求已齐全”。
- 检查定义包括受管输入、实际命令/检查器、环境与预期；可解析测试结果时检查必需用例、失败/跳过、测试数量等，不仅看 exit 0。
- 宿主校验每个条件有适用且成功的检查，产物版本匹配，无未决/过期事实；任务图闭包继续校验，但不替代条件覆盖。
- 非自动化条件列为明确人工验收项，不能被模型普通回复替代。
- 契约变化须版本化；范围/权限的实质改变使用既有用户授权流程，不能由 Advisor 为了通过验收删条件。
- 旧目标没有此契约时保留“legacy 宿主回执级接受”的历史，不回填虚构映射，不把它升级宣称为新级别验收。

验收报告应区分宿主执行证明、契约检查通过、模型相关性审查和真实人工/产品接受。即使映射齐全，也不等于数学证明所有业务语义正确；检查定义的质量、独立测试/审阅和现实环境验证仍不可省略。

**验收**：任一必需条件未覆盖、调用不符合既定受信检查定义（例如用 noop 替代测试）、版本不匹配、跳过必需用例或人工项未确认，均不能被“任务全 done”掩盖。若检查定义自身无效或不足，单靠结构映射仍不能识别所有语义问题，更不能自动宣称真实业务接受。

| validation/最终验收入口                     | 条件覆盖、版本适用与确定性事实检查                     | 只凭模型说“通过”或不断增加框架层         |

历史数据仅只读解释或显式迁移：不能推导出不存在的终态回执、原生许可、调用树、产物版本或需求映射。迁移不重放任务或业务启动；modern store 丢失不回落 v1。模式记录必须按明确的最新有效修订恢复，而不是任何历史 enabled=true 即启用。
