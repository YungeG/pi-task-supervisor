## 先看结论

- **可以并行准备**：P0 现状／兼容核对、P1 有限验收路线核对、P2 UI 材料与状态场景准备。这些是原准备依赖；本轮已另获代码与隔离测试许可，Main 正单写者实施，不启动并行 writer。
- **必须先串行完成**：K 由 Main 冻结共享契约；S 由一个写者交付真实、可编译的公共接口基线。只有文档签名、各分支没有同一份实际接口，不算可以开工。
- **基线完成后可并行**：A 确认核心、B 流程资格、E 有限验收、U 原生 UI。它们没有人为的 A→B→E→U 串行依赖，但必须遵守文件归属和写者上限。
- **最后统一汇合**：I 接实际入口和共享适配；V 验证与 Q 只读审阅可针对同一冻结候选并行；F 由 Main 最终核对。

这些是工程依赖，不是新增业务审批门。源码与隔离测试已经获准，不重复索取。技术细节与证据由 Main 负责；**Q 已由用户明确允许并完成，原发现及随后 settle/kwargs 遗漏均由 Main 复现修复，最终复核 OK，F 已核对接受**，不是用批准替代技术证据。

## 2. 真正的执行 DAG

```text
P0 ─┐
P1 ─┼── K ── S ──┬── A ──┐
P2 ─┘             ├── B ──┤
                  ├── E ──┼── I ──┬── V ──┐
                  └── U ──┘       └── Q ──┴── F
```

三种依赖必须分清：`C` 为共享契约／接口，`E` 为实际证据或候选产物，`W` 为写入占用和交接。逗号表示组内每个节点都产生对应边，不意味着组内节点互相依赖。

| 上游    | 下游    | 类型 | 具体跨越的产物或占用                                             |
| ------- | ------- | ---- | ---------------------------------------------------------------- |
| P0      | K       | E    | 当前调用链、旧 reader／宿主约束、不能回退的行为依据              |
| P1      | K       | E    | 有限验收路线、缺失证据及两个正向分支的可行性；不能凭名称推断支持 |
| P2      | K       | C    | 人类完整材料、选择草稿和动作后反馈的输入／输出要求               |
| K       | S       | C    | 共同版本、身份、失败语义、精确公开 symbols 与写集                |
| S       | A,B,E,U | C    | 同一实际公共接口基线；纯文档或各自 mock 不能替代                 |
| A,B,E,U | I       | E    | 可复现模块候选、针对性验证和明确限制，不是口头“完成”             |
| A,B,E,U | I       | W    | 分支停止写入并交接文件占用；集成期修改按下节归属或明确转交       |
| I       | V,Q     | E    | 同一冻结整合候选及有效契约、环境／依赖身份                       |
| V,Q     | F       | E    | 实际验证结果、审阅报告和发现处置，均覆盖同一候选                 |

按上述分工，不引入 A→U、E→B 等人为串行边。A 的基本正向路径使用既有有限 Node 能力，E 负责新增的有限外部场景。K／S 必须核实消费方所需真实原语已存在于公共或旧基线：如果实际上必须等某条线的新实现，就补上真实依赖或提取最小共享前置，不能用成功 mock 或伪造资格把隐藏依赖抹掉。

若消费方需要上游尚未冻结的字段，回到 K／S 修订公共契约，再重验受影响消费方；不得私下给接口加字段并称为独立并行。

## 4. 并行度与 Ready 队列

- **本轮**：Main 单一代码写者串行完成实施/验证；一个独立只读审阅器获准审查并复核发现。不启动并行 writer/workflow、不创建 worktree。当前源码候选已接受，不自动开始新的实现或发布工作。
- **未来未明确允许多写者时**：同一工作树最多 1 个写者；可有最多 2 条只读准备／审阅线，不因本计划而自动获得委派许可。
- **未来明确允许隔离并行时**：建议最多 2 个实现写者，各自独立目录／worktree，最多 2 条只读线；耗资源的完整验证同时最多 1 个。
- 并行所需目录、worktree、本地提交和清理对象，若需要额外权限，应在实施前集中列清楚；本计划不授予这些操作，不临时用“并行需要”绕过审批。获准后由 Main 先分配具体绝对路径、分支和回收条件，不放进扩展自动发现目录，避免运行会话意外加载候选代码。

建议排程：先并行收集 P0／P1／P2，Main 串行完成 K→S；随后优先把写入槽给 A 和 E，B、U 准备各自测试与材料。任一槽释放后，按解除关键路径的价值选择 B／U，不必等待同批所有兄弟结束。I 汇合完成后，V 与 Q 可并行，最后由 F 核对。

若只允许一个写者，A／B／E／U 按队列执行，DAG 不变；不应为“看起来并行”增加模块层或重复实现。没有一致隔离基线或共享文件占用未释放时，不能并行写入。

## 5. 基线、交接与变更规则

1. S 交付实际可用的公共接口和基线身份，所有实现分支从同一完整内容开始。只报 HEAD 而遗漏未提交公共接口不合格。
2. 若后续授权包含本地提交，可用冻结的接口基线提交；否则须给可复现源码快照和逐文件摘要，并证明每个隔离目录确实包含它。无法安全形成一致基线就保持串行，不擅自提交。
3. 各节点交接应包含：消费契约版本、公共接口基线、模块候选身份、实际改动文件、已运行检查／未验证范围、共享文件适配请求及仍持有的写占用。
4. I 只在分支结束或明确释放占用后接管；需要修改分支文件时，明确转交给 I，或退回原节点修复。不能两个写者同时修同一文件。
5. K／S 变化使受影响节点返回等待契约状态，不能由消费分支自行“兼容”出不同语义；其他无依赖工作继续。
6. 新增独立 writer／workflow、安装、推送、发布或业务执行仍须满足各自授权；文档排程不是启动许可。

## 6. 验证分配与 R0–R5 对照

A／B／E／U 各跑自己的最小红绿用例和直接边界，不重复完整矩阵。I 做跨线适配与短冒烟，V 对冻结整合候选集中完成必要完整验证，Q 独立审阅，F 核对发现和证据。候选变化后按影响与既有政策重验，不把旧结果标到新版本。

| 原修复分组                  | 在本 DAG 的落点                           |
| --------------------------- | ----------------------------------------- |
| R0 技术契约                 | P0,P1,P2,K,S                              |
| R1 诊断／资格               | B；真实入口接入归 I                       |
| R2 前置定义／联合确认／恢复 | A；公共基线归 S，真实 transport／入口归 I |
| R3 有限验收                 | P1,E；实际消费与源资格接入归 I            |
| R4 原生 UI                  | P2,U；真实确认 adapter 归 I               |
| R5 整合验证                 | I,V,Q,F                                   |

两个必需正向链路和故障／恢复清单见[集成验收卡](./50-integration-validation.md)。本轮完整门、SDK、CLI/PTY、包内执行与独立审阅已闭合，Main 已完成限定源码候选的最终接受。
