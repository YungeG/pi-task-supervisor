# P0／P1／P2／K／S：准备、共享契约与接口基线

节点状态、依赖和文件归属只在[施工索引](./README.md)维护。本卡记录准备依赖与 K/S 的施工契约，不单独授权运行或修改。原“仅文档”阶段已由[本轮实施契约](./01-execution-contract.md)记载的后续许可取代；当前实际完成/待审阅范围只看索引和验证记录。

## 1. 三条可并行准备线

| 节点          | 限定结果与输入                                                                            | 产出应回答什么                                                                                                    | 不做什么                                                          |
| ------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| P0 现状／兼容 | 对照原设计、修复计划及现有 preflight／acceptance／native answer／restore 调用链           | 原生来源、当前身份和持久化顺序；已有测试、旧记录／reader 保护；真实就绪与提示不一致的入口                         | 不把源码核对当实际运行验证，不重写历史接受记录                    |
| P1 有限验收   | 对照 `check-runner.ts`、`artifact-version.ts`、`qualified-evidence.ts` 及正式验收消费路径 | 精确代表场景、执行源和范围、close／exit、版本、结果语义与原始来源如何闭合；两个正向分支为何可行、还缺什么样本证据 | 不先选通用 Python／Bash 执行器，不把报告文件或 DTO 当私有原始回执 |
| P2 UI 场景    | 对照只读原型、`HumanMaterial`、`DecisionDraft`、`NativeQuestion` 和当前材料／反馈         | 首屏与完整材料、准确草稿选择、反馈状态及其输入字段；窄屏、取消、过期、异常时的示例                                | 不把浏览／草稿当批准，不自行决定联合身份或新增原生回应种类        |

各线返回独立材料，由 Main 汇入 K；不得并行编辑同一个共享契约文件。本轮实际由 Main 串行承担，材料/验证身份见索引；这不自动授予未来独立并行线权限。

### P1 必须精确解决的能力问题

当前正式检查是有限 Node 只读路径，输入／产物受 workspace 范围与实际版本捕获约束。外部守卫／Python 场景涉及不同执行与写入条件，不能只改显示名称就宣称支持。

P1 必须列出一个受控代表场景的准确执行者、允许对象、结果产生方、观察方式、owner 和正式验收接入位置；若需新增能力，明确最小扩展和现有调用者。检查器由本任务创建的分支，还须说明准备完成后通过哪条真实资格路线冻结定义、继续并取得结果。

仅凭源码推测可行不是已取得正向证据。必要隔离样本须在后续允许的验证范围内进行，记录失败和未知；不能以用户批准补证，也不能在无证据时让 K 把这条路线标为已支持。

## 2. K：Main 串行冻结的共享契约

下表是跨线必须一致的**契约编号与语义**，不是已经存在的 TypeScript 类型或 wire schema。K 必须进一步确定实际 symbols、字段、返回值、调用方、保存顺序及精确写集；未完成就不能把代码任务置为 READY。

| 契约                    | 必须冻结的内容                                                                                                           | 消费方      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ | ----------- |
| C-ID 联合材料与身份     | 真实 session／目标／预检来源，方案与定义版本、权限选择、完整材料身份；内容变化怎样影响各部分确认；不能将模型字段当 owner | A,B,E,U,I   |
| C-DEF 前置定义          | 启动前确认的要求／现存检查器输入，与执行后产物版本／结果分开；如何关联后续实际执行 owner；不接受未来任意检查器           | A,E,I       |
| C-PREP 准备与继续       | 准备范围的权限及自身验收依据、具体定义形成后的合法转换、原 Start 意图保持、用户暂停与未知执行的优先级                    | A,B,E,I     |
| C-ACT 动作资格          | 输入事实来源、允许／阻塞／不支持、当前真实动作及参数、执行者、影响和剩余门；显示无副作用，实际执行重新验证               | B,U,I       |
| C-EVI 有限验收          | 支持的实际执行与结果对象、范围和版本、原始来源／close 证明、消费资格与不支持的失败表面；禁止 DTO 代替原始证明            | A,B,E,I     |
| C-VIEW 人类材料与草稿   | 同版完整材料、关键风险、来源标识、权限选择草稿的类型与校验；草稿不产生 `NativeAnswer` 或持久权利                         | A,B,U,I     |

### 不能留给实现写者猜的决定

- 在预检／规划阶段采用哪个已有可信来源绑定定义，不用旧执行目标代替；不因缺未来产物而创建假的版本事实。
- 一次明确操作怎样覆盖精确选择和定义，哪些事实必须完整可信落地才开放相应执行；不能直接复用当前业务“允许”结果。
- 半写时哪些是已有完整事实、哪些是可修投影、哪些必须保持未知；恢复不能重新索取或重放已保存 Start。
- 普通源码／产物进展只更新相关证据，不自动重收未变化业务权限；实质材料变化不得挪用旧确认。
- 新定义所需的真实确认与重复业务授权不是同一件事；两个正向分支都要有合法路径，不能靠删门、重建目标或重复 Start。
- 总材料、单事实及原生审核的容量怎样保持完整且有界；超限给具体字段和缺口，不裁掉条件、不默认提高预算。

本轮没有让用户决定 schema／hash 等实现细节。若发现目标或权限约束本身冲突，Main 应先说明实际冲突；其余技术证据与接口由 Main 收敛。

## 3. S：实际可编译的公共接口基线

**文档里冻结一个返回值，不等于并行分支已经拥有这个返回值。** K 通过后，先由一个基线写者落地实际公共类型、必要纯校验和兼容导出，验证后再分叉 A／B／E／U。

已核对的现有接缝：

- `NativeQuestion` 带真实 frame；`NativeAnswer` 只有通过私有登记才能使用。
- `HumanMaterial` 是 `context/summary/sections` 的显示数据，不是证明。
- `DecisionDraft` 是局部草稿，当前有 `kind/index/value`，不能直接当联合权限选择协议。
- `FlowFacts` 是供只读判断的事实；`nextFlowStep` 目前返回文字，不能让文字成为控制许可。
- `NativeCheckInvocation/NativeCheckExecution` 及 `ArtifactScope/ArtifactVersionV1` 有具体范围和来源约束，不能改名即外推为任意外部执行。

S 的交付要求：

1. K 为每个公开接缝选定真实落点和 exact type／返回值，优先复用现有 Module；不为并行强造一层通用框架。
2. 需要跨线的类型和兼容导出实际存在、能够编译；不让各线自行复制一套同名接口，或用 `any`、伪造 token／回执蒙混通过。基本正向路径需要的真实共享原语也必须在 S 或旧基线中具备，包括必要的受信来源生产／校验；若它实质上只能由另一实现线或 I 交付，就调整 DAG 或合并实际不独立的节点，不能先用成功 mock 掩盖该依赖。
3. 新能力在实现／来源不具备时明确拒绝或不支持，不回退成更宽权限；基线本身不创建用户批准、启动或验收通过事实。
4. 旧入口及保留字节／行为经过针对性核对；新记录 reader 与启用次序有明确交接，不能先写新事实再补 reader。
5. 记录基线内容、消费契约版本、实际检查结果与保留文件；按索引交接文件占用，再允许分支实现。

基线可用获准的本地提交或可复现源码快照标识，不能用不含未提交接口的旧 HEAD 冒充。没有形成一致隔离基线的条件时，保持单写者串行。

## 4. 最小验收与交接

P0／P1／P2 的事实、未知和未运行项分别列出，不把“有报告”当通过。K 要交付可核对的消费表、版本／失效表、失败矩阵、准备分支和 precise write set；S 要交付真实公共接口基线及编译／直接边界结果。

S 的首个检查应能识别不兼容类型和旧调用者行为变化，检查期间不启动新流程。A／B／E／U 全部消费同一基线；一条线需要改公共字段时回到 Main，不在局部 fixture 里偷偷扩接口。

完整验收、源码审阅、UI 产品接受均不属于 K／S 已经完成的事实。具体实现和验证仍受后续授权与本索引状态约束。
