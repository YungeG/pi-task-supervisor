# Code Mode completion: local candidate scope

Nested checks must not become fresh merely because their parent returned. This candidate records actual SDK invocation ancestry, waits for a qualified root boundary, and appends a separate eligibility attestation. Original receipt bodies, hashes, epochs and `eligible` fields remain unchanged.

This is local source, not a claim about the revision loaded in a running extension. No real session configuration, mode, permission or first-start is changed by enabling the implementation in an isolated test.

## Qualified host surface

The qualified sample uses Node 25.9.0 and SDK 1.1.0, the genuine builtin Code Mode tool, its original schema identity/description/source metadata, and a trusted host factory with `models: false`. SDK `parentToolCallId` events determine ancestry. Slash-separated IDs, tool names, model arguments and script text do not.

Default models-enabled Code Mode is **not qualified** for this optimization. Its model/catalog operations lack a complete tool-event surface. Store changes, image output, output spill, unexplained or failed calls, unfinished descendants and unknown versions also disqualify a root. This is a capability boundary, not advice to change the real session's settings.

Ordinary non-container hosts retain their original flat completion path. Task-only nested check completion is unavailable on this SDK's original receipt surface: native task-only custom results do not durably preserve structured exits. Missing exit data is not zero. Existing owner, execution-registry, permission, first-start, human-control and budget gates still apply.

The qualification does not establish semantic test coverage, useful business change, ignored/external input coverage, arbitrary third-party background-writer quiescence, or a broader SDK/version matrix.

## Completion sequence

1. Admit a bounded invocation under its actual current owner and actual SDK parent.
2. Retain original host results, then observe the separate SDK kernel-end callback.
3. A nested reviewing-to-done request validates its original successful structured zero-exit review receipts and records a **deferred intent**. Its response explicitly says `completionState: "deferred"`; the task remains reviewing. Mixed transitions must be split.
4. At the existing safe native boundary, seal only a complete, quiet, qualified root. Neither `tool_result` nor entering `tool_execution_end` immediately completes a task.
5. Append an attestation only for ancestry-explainable original ineligibility. Recheck current owner/control frame, actual artifact version, receipt attribution, overlapping or later writers, settlement, evidence capacity and normal completion gates.
6. Run the original task persistence/binding procedure once, then record the intent's immutable disposition. Final freshness and review consume the same effective eligibility query.

A real earlier write followed by validation can qualify; the container is not reclassified as readonly. A later same-byte write or real overlapping writer cannot be hidden by equal content hashes. A post-seal host write also invalidates applicability. An intent is not progress, authorization, task completion or goal acceptance.

A repeated identical pending request reuses its intent. A conflicting request, changed task or stale context is rejected/invalidated rather than reinterpreted. A failed nested call can disqualify the whole root even when script code catches the error.

## Holds and recovery

- Human pause/stop/revoke, manager/Session/Goal/mode movement and unknown persistence/execution remain stronger than completion. Late results do not adopt a new owner.
- A restored active/unknown root is not current live SDK work. SDK idle, abort acknowledgment and `close_unknown` do not settle it. Do not replay tools to manufacture closure.
- Cold queued intents never execute business or checks automatically. An old attestation without a current host frame/input verification is not a fresh check.
- If a done snapshot was actually confirmed but its derived binding/disposition is incomplete, inspect the original group, then use the native command:

  ```text
  /task-supervisor repair-completion <intentId>
  ```

  This requires a confirmed quiet current owner/journal, the exact original done snapshot and sealed qualification history. It repairs only missing binding/disposition metadata. It does not advance a task, rerun a command, call a provider, replenish budget, grant permission or freshen validation. Repetition appends nothing. Invalidated/uncommitted intents cannot be reapplied this way.

A held completed board still cannot be reopened through generic recovery. Review-only retry and any independently qualified final validation retain their existing restrictions. No chat confirmation substitutes for an original native human response.

## Bounds and evidence

- At most **512 active nodes**, depth **16**. Completed sequential nodes do not evict a live parent. The canonical native history remains ordered/compact, not recursively embedded subtrees.
- Active callback leases are separate from bounded recent results. Closed current-frame retention is bounded at 128 roots; eviction cannot invent freshness.
- Pure native decoding caches at most 8192 entries / 32 MiB of serialized retained projections. Default returned nodes have isolated compound fields; explicitly readonly internal inspections share recursively frozen nodes only. One private incremental control fold per actual manager is bounded to 8192 physical nodes / a 32 MiB source; otherwise it falls back to a cold strict fold.
- Cache reuse never skips physical reads, complete-tail/header/ancestry/limit checks or SDK mirror verification. Runtime/manager/path/header/branch/prefix changes rebuild. Cache state is not permission, durability or quiescence evidence.

Owned real SDK/QuickJS producers and exact-prefix cold recovery are in `test/codemode-supervisor-smoke.mjs` and `test/codemode-recovery-smoke.mjs`. Instrumented SDK tests also cover actual overlap, unfinished children, native pause, uncertain append, repeat/conflict requests and post-seal writes. Negative decoder/cache mutations are not positive execution proof. UI stubs and an explicit legacy fixture start do not prove human identity, real CLI/PTY behavior or production acceptance.

The 1/10/100/500/1000 owned benchmark checks complete native history even after SDK diagnostic `nestedCalls` truncates at 256. Decoded/folded node counts are linear in that bounded sample. **Whole-file byte IO/hashing and total latency are not claimed linear**; an earlier 1000-check sample took about 174 seconds and a subsequent formal arm timed out at 987 checks. After removing redundant private validation copies and sharing only frozen readonly decode nodes, a bounded sample completed in about 140 seconds / 559 MiB peak RSS under the unchanged 180-second root limit. These resource limitations and the separate 100-full-registration investigation remain visible for combined/resource acceptance.
