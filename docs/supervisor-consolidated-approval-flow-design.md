# Supervisor 集中审批与审核前移流程设计

记录日期：2026-10-27。

状态：**用户已确认设计方向，本轮仅记录设计，不施工。实施契约尚未冻结，新流程尚未实现或验收。** 本文中的“应／必须”是后续设计要求，不是对现装能力的描述，也不是启动、合并、提交、推送、安装或发布的授权。

本文细化[执行前授权预检设计](./supervisor-permission-preflight-design.md)的集中确认原则，不回写此前实现、批准和交付的历史事实；不把[既有实施契约](./supervisor-permission-preflight-implementation-packet.md)自动升级为本次改造的实施批准。

具体缺口、修复顺序、源码触点和完成判据见[集中审批流程修复计划](./supervisor-approval-workflow-repair-plan.md)。修复计划仍有待冻结的技术契约，不是已经施工或实施就绪的声明。

## 1. 设计结论

核心原则：**提前发现、按范围批准、范围内不重复问、超范围仍需确认。提前确认决定，事后核验事实。**

- 推进前只读盘点整个计划中可预见的权限和执行条件，尽量合并为一次明确的集中审批。
- 每个用户可见步骤结束，都说明结果、下一步、执行者、是否需要用户及执行影响；不要求每个内部工具调用都点“继续”。
- 决策材料面向用户阅读：先用清楚的语言说明问题、选项、关键范围、风险及选择后的动作，再分层提供技术证据，不直接把原始 JSON、哈希和内部状态堆给用户。
- 统一交互入口不等于混同权限批准、验收定义确认、首次启动和结果验收的含义。
- 保留独立首次 Start。Start 的含义是开始本次已界定且可合法推进的执行范围，不是提前宣告整项目标可以验收。
- 减少的是用户操作和内部协调负担，不是安全校验；不新增另一套权限引擎、任务板或恢复调度器。

## 2. 为什么需要调整当前流程

本次只读检查的会话出现了以下路径：

```text
只读预检 → 权限批准 → Start → 建板／编译
→ 才发现验收合同未绑定 → 补合同提案 → 暂停并让用户寻找审核命令
```

安全门阻止了未满足条件的托管执行，但用户已经表达启动意图，随后仍需协调多个内部步骤。这不符合执行前集中准备、范围内持续推进的产品目标。

核对时的源码基线为 `0f8f5f83e01a9db1d1e2c4662046471797897ab0`，存在以下限制；它们是现状，不是新设计要求：

- `src/acceptance-runtime.ts::preCompileOwner` 要求 Supervisor 为 `active`、有实际 goal owner，且任务板尚未编译。预检阶段提交提案不等于可以完成可信绑定，`paused` 也不能直接进入该审核。
- `prepareContractBinding` 通过 `captureCheckVersion` 捕获输入和产物的实际版本。当前读取路径要求文件存在；不能直接用来要求未来正常产物在启动前已经存在。
- 当前权限回应和合同定义回应属于不同的原生确认路径，不能直接拿已有的业务“允许”或 Start 回应充当合同绑定证明。
- `nextFlowStep` 的通用建议与合同编译门尚未完整协调；推荐动作可能缺必要参数，或在当前暂停状态下仍会被拒绝。

因此，本次改造不是只移动命令、修改提示词或删除 `active` 检查，而是要明确预检确认与执行身份的衔接、不同阶段的就绪条件，以及统一的下一步引导。

## 3. 哪些审核前移，哪些必须留到执行后

| 判断                                       | 合适时点                                         | 不能据此声称                                   |
| ------------------------------------------ | ------------------------------------------------ | ---------------------------------------------- |
| 业务权限：允许做什么、作用范围和限额       | 执行前，尽量集中确认                             | 已有技术权限就等于获得用户许可                 |
| 验收要求：达到什么结果才算完成             | 执行前明确并确认                                 | 已经满足这些要求                               |
| 具体检查定义：如何检查、采用哪个受信检查器 | 已有且可明确审阅时前置；尚待创建时如实标记待冻结 | 尚不存在的检查器已受信，或任意后续实现都获认可 |
| 首次 Start：何时开始本次执行               | 已界定的当前执行范围具备合法推进条件后           | 新增权限、清除其他独立暂停或通过验收           |
| 产物版本、真实执行结果和最终验收           | 实际产物和证据产生后                             | 可用启动前的批准预先判定成功                   |

必须区分两条规则：

> **范围未变，仍适用的业务权限不重批；产物变化，相关验证证据仍须更新。**

普通代码进展、批次切换或新的验证 epoch，不自动撤销业务授权；旧通过结果也不能跨产物版本充当新证据。检查逻辑、作用范围或风险发生实质变化时，重新确认对应内容，不能挪用旧版批准。

## 4. 集中审批包与正常路径

### 4.1 先盘点，再集中呈现

Main 只读分析当前获准且必要的材料，覆盖全计划中可预见的操作，不只看眼前一步。清单至少区分：

- **已获授权**：有真实依据，动作、目标、环境、限额和有效条件仍适用，不重复申请。
- **必需权限**：缺失将阻塞已界定方案或其必要验收。
- **可选权限**：拒绝后有明确、仍满足约定目标的替代路线。
- **未知事项**：对象、影响或必要条件尚不明确，不能当作默认允许。

完整审批包应集中呈现目标和方案、权限选择、验收要求、可确认的检查定义、待冻结事项、预算／限额、禁止事项、风险与回退、替代路线及重新确认条件。不得为了通过容量限制省略必需条件或把未知风险包装成授权项。

原任务授权已覆盖的简单、可逆、范围内工作，不额外制造业务审批。全程预检也不等于允许读取凭据、试部署、改变宿主策略或先执行动作来探测权限。

### 4.2 一次明确集中确认，分别保留其含义

目标是让用户在同一个原生入口审阅完整材料，明确进行一次集中确认，并可选择部分权限、拒绝或要求替代方案。交互必须清楚说明该确认具体覆盖哪些权限和哪些检查定义。

后台分别保留权限选择与验收定义的可信事实，共同对应准确的目标、方案／定义版本和作用范围。提案、模型整理、流程图、审阅 OK 或 READY 都不能产生这些权利。现有单独的业务“允许”回应不能直接伪装成联合确认。

**集中审批不代表首次启动，不代表产物通过，也不取消宿主平台本身强制要求的独立确认。**

必需项被拒绝或未知时，不启动依赖它的原方案。可以提出独立且已获准的缩小范围或替代方案，但不能悄悄缩减目标后宣称原目标完成；实质修订须明确展示变化，并取得适用于当前材料的确认。

### 4.3 正常路径

```text
用户提出目标与已有边界
→ Main 只读盘点权限、验收要求、检查定义和环境缺项
→ 形成完整可审的审批包，明确已知与待冻结事项
→ 用户一次明确集中确认，分别保留权限／定义事实
→ 系统复核本次执行范围的就绪条件，显示准确下一步
→ 用户独立 Start
→ 系统在有效授权内分批执行、验证和自动续跑
→ 按约定完成必要人工验收与结果交付
```

不得先显示“可以 Start”，再在用户启动后才发现本可提前准备的审批材料。另一方面，“就绪”也不能被解释为所有未来产物、测试脚本和实现细节都必须提前存在。

## 5. 检查器或产物尚不存在时，不制造新的启动死锁

审核前移的范围是执行前可以合理决定的事项，不是把所有审核挤到 Start 前。

- **已有检查器、尚未生成正常产物**：应能确认验收要求和该检查定义；未来产物的实际版本、测试观察和通过结论留到产生后取得。
- **本应已有的检查器或必要输入缺失／未知**：明确报告缺项，阻塞依赖它的动作；不能假称已冻结或要求用户点同意补证据。
- **任务本身需要创建检查器**：先确认验收要求，明确哪些具体定义仍待形成。将必要准备工作纳入有明确写集、效果和自身验收依据的授权范围；准备完成后再冻结具体检查器，不能事前认可任意未来代码。
- 若当前存在可独立、合法推进的准备工作，不因其他未来检查器尚不存在就无条件卡住整项目标；若没有这样的范围，则保持明确阻塞，不开放相应执行。
- 已有审批包和有效启动意图明确覆盖的准备工作，不仅因阶段名字变化就重新审批或重新 Start；确有新权限、实质定义变化或必须由人作出的新判断时，明确展示变化并取得相应确认。

这不是绕过当前合同门的操作指南。准备阶段怎样与真实执行 owner、检查定义和任务资格衔接，必须在实施契约中冻结；当前代码仍不能仅靠命令重排实现此路径。

## 6. 每步之后都给出可信的下一步

统一提示至少说明：

1. **结果**：成功、部分完成、取消、失败、未知或仍有阻塞。
2. **下一步**：实际可执行的动作，按钮或完整命令自动带入准确参数，不让用户复制内部 UUID 来猜入口。
3. **执行者**：系统、Main、用户或既有执行 owner；不以“找维护者”代替已能进行的诊断。
4. **是否需要用户操作**：不需要时明确说明，不逐工具调用索要“继续”。
5. **执行影响**：仅查看／记录，还是会首次启动、恢复或产生已获准的副作用。
6. **其他阻塞**：解除一项门后仍需满足什么，不推荐马上会被另一项门拒绝的动作。

示例：

```text
权限与本次可确认的验收定义已保存。
下一步：系统复核当前执行范围；满足条件后提供独立 Start。
需要你操作：目前不需要；尚未开始执行。
```

```text
守卫回归通过。
下一步：系统运行本范围内已批准的旧 Store 测试。
需要你操作：否。
```

复用现有 `flowFacts`、`nextFlowStep` 及各 owner 的实际资格依据，让状态展示、命令结果和助手提示一致。执行时仍重新校验，不将显示的按钮当作新权威；不新增第二套允许规则或自动恢复器。

受信、范围内的只读状态／帮助／阻塞说明应可查看；不能据此把任意 Bash、codemode 或工具自报的 `readOnlyHint` 放行。无合法下一动作时，如实说明所需证据、处理人和不能执行的范围。

## 7. 决策文档必须让用户能够作出知情选择

本节记录用户补充的可读性要求，适用于独立决策文档、集中审批包和原生确认界面；不是只美化 Markdown 或给原始 JSON 换皮。以下为设计要求，尚未做真实 TUI 或 SSH 阅读验证。

参考案例、现有呈现能力及低保真布局见[审核 UI 调研与布局建议](./supervisor-review-ui-research.md)。调研建议默认采用单列审核单、分区完整材料和稳定操作区，宽屏／浏览器仅作辅助；这是待确认的交互方向，不是组件选型、实施批准或已经改善实际 UI。

### 7.1 先说明要决定什么，再给证据

- 标题直接说明具体决定，不用 UUID、P0／G0、内部状态名或长路径代替问题；必要术语首次出现时解释。
- 首屏给出当前事实、尚未核实事项、本次唯一明确的决定、可选路线和推荐理由。需要多个独立选择时分组说明，不把它们混成含糊的“同意／继续”。
- 每个选项说明会做什么、不包含什么、关键权限和预算／限额、风险与回退，以及拒绝、部分批准或暂不决定会有什么影响。没有额外费用／不可逆影响等结论须有依据，未知就写未知。
- 关键作用范围、真实数据影响、禁止事项、未知风险和本次变更必须显式呈现。首屏可以概览，但确认前应能完整阅读关键材料，不能只藏在技术附录或为了塞进一屏而省略。
- 解释选择后是否仅保存确认、是否仍需独立 Start、由谁做下一步；已有确认、待确认和未通过验收必须区分。
- 使用短句、明确小标题和有意义的选项名称；范围和权限用清单，真正的选项差异用短表，长路径／命令可换行或复制，不要求用户手输内部 ID。

### 7.2 用户说明与机器证据分层，但必须对应同一材料

用户主视图负责支持知情选择，技术附录保留完整来源、版本、精确路径、参数、标识和证据。不要求用户阅读原始记录才能找到主要风险，也不删减机器绑定所需的材料。

两层必须对应同一审批对象、范围和版本。关键数值、限制和选项效果应从同一份受保护材料一致呈现，不能依赖模型自由概括后把它当成权威。展示过期、相互矛盾、关键材料超限或不完整时，不允许用简短摘要替代完整确认；应明确说明缺项或提供受信的完整阅读方式。

单纯打开文档、翻页或勾选“已阅读”不证明用户理解，也不构成批准。预览页面只负责阅读，不自动成为新的授权入口；最终确认仍需受信原生操作及其匹配见证。

SSH 场景不能只给服务器上的 `file://` 链接。应提供当前环境可用的阅读入口，例如终端内可读 Markdown、自包含 HTML 下载或明确的本地端口转发方法；不能假定本机能直接打开服务器路径，也不能声称未核实的预览服务已经可用。预览不应默认公开到公网或暴露凭据。

### 7.3 决策说明的最小模板

以下只是呈现模板，不是当前业务申请或授权：

```text
需要你决定：<一个具体问题；相关独立选择分别列出>
当前情况：<已核实事实、为什么需要决定、仍有哪些未知>
推荐方案：<建议及理由；有依据才作推荐>
可选路线：<各选项的实际差异，包括拒绝／暂不确认的影响>
执行范围：<会做什么、不会做什么、作用对象、权限与限额>
主要风险：<数据／费用／不可逆影响、回退及未知事项>
选择之后：<仅保存还是会执行、是否仍需Start、下一步由谁做>
依据与详情：<完整关键材料和技术证据的可用阅读入口>
```

## 8. 执行中的再次确认与技术阻塞

- **范围和证据状态仍适用**：自动推进，保留必要的运行时校验，不反复申请已获权限。
- **新增权限、成本、风险、环境变化或真实业务选择**：在动作发生前集中说明新事项与影响；只阻塞受影响动作及依赖，确属独立且已获准的工作继续。
- **失败、证据缺失、状态冲突、执行结果未知**：Main／程序先只读诊断并保留事实。用户批准不能补造证据，不能把未知执行当失败自动重派，也不能将失败包装为通过。
- **技术处理需要新的破坏性操作、外部副作用或费用**：另行取得对应范围的授权；诊断不是任意修复许可。
- **用户主动暂停、撤销、停止或独立人工门**：原事实继续有效，不因另一项审核完成而顺带解除。已有批准不等于新的恢复意图。

每次操作完成后复核剩余门。仅在原启动意图仍有效、当前执行资格成立且不存在用户暂停等阻塞时继续；不能把合同绑定本身当成新增执行许可。

## 9. 联合确认、半写和重开的安全要求

集中确认增加的是交互整合，不减少精确身份与持久化要求：

- 同一次操作必须明确对应权限选择、验收要求／定义版本、目标和作用范围；不得跨会话、目标或版本挪用。
- 任一必要事实未完整可信落地，对应执行保持关闭；不能只凭“权限已批准”假定合同也已确认。
- 已有完整原始控制和见证，仅派生投影缺失时，只考虑精确、可验证、幂等的元数据恢复，不重新索取同一次批准，不生成新的原始批准。
- 原始确认、物理见证、写入或派发结果无法确定时，保留 hold 与诊断，不自动重问、重写或重放。已有一次启动记录不因缓存缺失获得第二次派发机会。
- 重开、压缩、切树、撤销和迟到结果均须重新验证实际来源和适用性；不能凭恢复后的摘要或旧显示推断许可及进程存活。
- 普通产物进展不顺带清除仍适用的业务授权；材料实质变化也不能以减少提示为由继续使用不再适用的旧确认。
- 预算和累计用量不因普通恢复清零；技术恢复不等于续额，也不清除其他 owner 的独立 hold。

联合身份、确认载体、见证／日志的写入顺序、失效粒度、失败优先级和跨重开恢复能力尚待实施契约冻结。本文不选择新的 wire schema，不授权 writer 临场补造这些规则。

## 10. 实施前必须冻结与验证的事项

以下是后续要求，**本轮未实现或运行这些验证**：

| 场景／契约                           | 必须证明的结果                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------ |
| 预检阶段的定义确认与执行 owner 衔接  | 只适用本方案的本次执行，不借旧目标记录或旧批准                                       |
| 已有检查器＋尚不存在的新产物         | 可确认规则，不提前产生版本证据或通过结论                                             |
| 检查器缺失、输入未知、准备工作未获准 | 准确阻塞，不假称受信，不以用户批准补证                                               |
| 检查器由本任务创建                   | 仅推进明确获准的准备范围；具体定义形成后按规则冻结，不无条件要求所有未来检查器先存在 |
| 集中确认后的任一保存点失败           | 必要事实不齐不执行；不重复索取已有完整确认、不跨版本赋权                             |
| 已有 Start 确认、投影／派发结果异常  | 查明真实记录与执行结果，不自动重复 Start 或派发                                      |
| 部分批准、拒绝必需项、可选项替代路线 | 不执行缺权动作，不虚报原目标完成；实质修订有当前版本确认                             |
| 产物正常进展与定义实质变化           | 前者不重复收业务授权但更新验证证据；后者不沿用失效确认                               |
| 暂停且合同未绑定、决策与故障并存     | 提示给出合法顺序、准确参数和执行影响，不推荐仍会被拒绝的动作                         |
| 重开、切树、撤销、迟到结果或未知执行 | 保持来源闭合、暂停与未知状态，不补批准、不重复询问或重派                             |
| 范围内正常分批推进                   | 用户无需逐步点继续，每步仍有清晰结果与下一步                                         |
| 只读帮助及结构／路径／容量错误       | 受信查看入口可用；错误指出实际字段和限制，不靠裁掉验收条件过关                       |
| 决策材料的主视图与完整范围           | 首屏能找到问题、选项和影响；关键范围、风险、未知及拒绝后果在确认前可完整阅读         |
| 用户说明与机器材料的一致性           | 同一对象和版本的权限、数值、限制及选项效果一致；不接受过期或丢失条件的摘要           |
| 长材料和 SSH 阅读                    | 不因长度省略关键内容；提供实际可用的阅读方式，不将预览或翻页当作批准                 |
