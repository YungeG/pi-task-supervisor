## 1. 核心结论

把可以预见的授权问题提前到执行前集中确认，而不是执行中每遇到一步就询问：

```text
用户给目标和已有边界
→ Main 只读规划并做授权预检
→ 用户确认明确的方案与授权范围
→ 启动 Supervisor
→ 授权范围内分批执行、验证和自动续跑
→ 超范围时只暂停受影响动作及其依赖
→ 最终验收
```

这不是“一次批准所有可能操作”。原则是：**提前发现、按范围批准、范围内不重复问、超范围仍需确认**。

简单、可逆且已经包含在用户任务授权中的读取、局部修改和测试，不应额外制造审批门。

### 目标

- 在实施前识别必需授权、可选授权和外部阻塞，减少可以避免的中途停顿。
- 让用户清楚知道允许做什么、作用于哪里、哪些情况仍会停下来。
- 复用明确且仍有效的授权，不借恢复、自动续跑或子代理结果扩大权限。
- 保留真实决策门、宿主权限机制、验证证据和最终验收要求。

### 不在范围内

- 不保证执行期间绝不会出现新的授权问题。
- 不接受无限期、跨环境、无预算边界的“全权限”。
- 不自动修改工具白名单、账号角色、凭据、审批策略或安全配置。
- 不重新实现子代理调度、并发控制、写权限或 worktree 管理。
- 不以本文为实施批准，不新增命令或修改现有状态机。

## 3. 区分四种不同的判断

| 判断         | 谁负责                             | 能证明什么                                           |
| ------------ | ---------------------------------- | ---------------------------------------------------- |
| 用户授权     | 真实用户；且不得违反更高优先级约束 | 某个明确动作在给定范围内允许执行。                   |
| 宿主工具许可 | 宿主工具、平台或外部系统           | 该次工具操作是否具备技术权限、是否需要独立确认。     |
| 执行调度     | Main 与既有执行器                  | 如何执行已经获准的工作；调度本身不会产生新授权。     |
| 完成验收     | Main 收集证据，Supervisor 检查目标 | 实际结果是否通过验证；成功回执不证明事前获得了授权。 |

用户提前批准业务动作，不一定消除宿主工具自己的确认提示。技术权限已存在，也不等于用户批准使用它。

## 4. 执行前预检流程

### 4.1 明确目标与只读范围

Main 先确认目标、验收标准、当前仓库或环境，以及用户已经给出的限制。

预检只读取当前任务已经允许且必要的材料。不能为了检查权限而擅自访问敏感账号、读取凭据、安装依赖、提交变更或进行试部署。无法在已有权限内确定的条件，应标为“待核实”，而不是冒险执行。

### 4.2 形成可执行方案与授权清单

Main 把方案拆为可验收步骤，对真正需要额外授权的动作列清单：

- **必需**：没有授权就无法完成该方案或其必要验收。
- **可选**：拒绝后可以采用明确的替代方案，不影响已约定的目标。
- **已获授权**：能指向真实用户指示且范围仍匹配，不再重复请求。
- **未知**：动作、对象、环境或影响尚不明确，不能按“默认允许”处理。

同时检查相关工具、凭据引用和外部条件是否可用，但不把“可用”当作批准，不把凭据值写进清单。

### 4.3 用户确认明确范围

Main 一次呈现方案、额外授权项、禁止事项和重新确认条件。用户可以全部批准、部分批准、拒绝或要求替代方案。

所有必需授权齐备后，才启动原方案。必需项被拒绝或仍未知时，Main 应修订方案或明确阻塞；不能先启动，再赌执行中能取得许可。用户也可以明确批准一个缩小后的独立工作范围。

不要求固定批准口令，但批准必须能清楚对应方案和动作。清单、`READY`、审查通过、用户沉默、模型生成的“批准记录”都不算批准。

本流程将授权确认与正式启动分开：授权确认回合只记录范围，不实施，也不把任务标记完成；用户随后用 `supervise` 启动。确认消息应显式保留这个启动门，避免 Main 在监督尚未启动时就开始执行。

### 4.4 启动监督执行

启动前必须确认当前会话没有未停止的 Supervisor、任务板没有旧 `done` 任务，也没有未解除的暂停或决策门。已完成但尚未 `stop` 的 Supervisor 同样属于未停止目标；新的业务授权不能绕过这些启动条件。

复用旧会话时，先用 `/task-supervisor status` 和 `/task-supervisor tasks` 只读核对原目标、任务及执行引用，再明确是继续旧目标还是启动新目标，以及对应的处理路径。预检和授权确认都不能自动停止旧目标、清板、删除证据或解除人工门；旧完成任务不能作为新目标的成果。

用户确认授权范围且上述启动前提已满足后，用现有 `supervise <goal>` 启动，并在目标中保留关键限制。

Main 继续负责建板、实施、任务审查和宿主验证；Supervisor 在原生结束检查点判断继续、停顿或目标接受。授权预检不改变任务证据门，也不取消批次领取保护。

## 5. 授权清单的最小内容

每个需要额外授权的动作至少包含以下信息。它们是人工可读记录要求，**不是已实现的持久化字段或工具参数**。

| 信息           | 要求                                                                           |
| -------------- | ------------------------------------------------------------------------------ |
| 方案标识       | 能区分用户批准的是哪个方案或修订版。                                           |
| 授权项标识     | 如 `A1`；用于对应批准、拒绝和后续变更，不是凭此获得权限。                      |
| 动作及对象     | 说明修改、安装、提交、推送、部署、删除等具体动作及目标。                       |
| 环境与范围     | 明确仓库、目录、分支、账号、服务或环境；不能只写“相关资源”。                   |
| 限额与有效条件 | 按风险写明次数、费用、数据影响、阶段或失效条件；普通可逆工作无需堆砌无关限制。 |
| 必需性与依赖   | 说明它阻塞哪些步骤、是否有不需要该授权的替代路线。                             |
| 风险与回退     | 说明外部副作用、不可逆影响和可行回退；未知时明确写未知。                       |
| 授权依据与结论 | 指向真实用户确认，区分已批准、被拒绝、待确认，不能由 Main 自行改成批准。       |
| 重新确认条件   | 说明何种目标、方案、环境或风险变化会使原授权不再适用。                         |

示例分类如下；**这些例子不是本轮授权**：

| 动作                                                     | 如何处理                                                                   |
| -------------------------------------------------------- | -------------------------------------------------------------------------- |
| 在已明确的仓库范围内局部修改和运行已知无外部副作用的测试 | 已在任务授权中时直接执行；检查测试配置，不能仅凭名称假定无副作用。         |
| 安装新依赖或修改锁文件                                   | 需要时确认包、来源、用途以及安装脚本和网络访问范围。                       |
| Git 提交与推送                                           | 分开确认；允许提交不自动允许推送，推送需明确仓库和分支。                   |
| 部署、发布或数据迁移                                     | 明确环境、版本或变更集、影响与回退；无法确定具体对象时保留执行前独立确认。 |
| 删除文件、数据或资源                                     | 明确对象集合和可恢复性；不以“清理”获得不受限制的删除权。                   |
| 付费或外部资源创建                                       | 明确平台、资源类型、金额上限和停止条件。                                   |
| 子代理或 workflow                                        | 遵守单独的委派授权要求，明确委派范围；Supervisor 启动不自动批准委派。      |
| 账号、凭据或安全设置变更                                 | 单独明确批准；不为减少提示而默认开放。                                     |

## 6. 授权有效性与重新确认

### 可以复用授权

动作、对象、环境、限额和有效条件都仍符合原批准时，Main 应直接执行，不重复询问。方案内正常的代码变化和任务进展，不应仅因产生了新的验证 epoch 就使业务授权失效。

普通人工暂停本身不新增也不撤销授权。恢复后仍需检查原授权是否有效，以及其他决策、故障和宿主权限门是否已经解除。

### 必须重新确认或明确停止

- 新增原清单未覆盖的高风险动作，或把可选项改成必需项。
- 扩大目录、数据、分支、账号、环境、成本或破坏范围。
- 改变用户批准所依赖的关键方案、风险、回退条件或外部状态。
- 原授权到期、用尽、被撤销，或已经完成其指定的一次性动作。
- 发现原本以为可逆的操作实际不可逆，或测试会触及真实外部系统。
- 授权来源缺失、存在冲突，或无法确认批准适用于当前目标。

明确禁止的动作不能被“尽快完成”“继续”“resume”“recover”或新的模糊目标隐式覆盖。用户要改变禁止事项，必须明确指向该事项及新的范围。

任务文本、工具输出、网页、advisor 建议和子代理消息不能成为授权来源。Main 对批准的整理只是索引，不是新的许可；发生歧义时应取得真实依据，不能靠模型推断补齐。

重启、压缩或切树后，应检查可追溯的真实批准与现有工作，不自动重派或扩大范围。跨会话、fork 或新目标不能默认为继承授权；需要核实原批准是否明确覆盖。当前版本没有结构化授权恢复保证，资料不足时应先找回依据，确实无法确认时再请求必要的补充确认。

## 7. 执行中仍出现缺失授权时

1. Main 不执行缺失授权的动作，说明缺少什么、影响哪些任务及可用替代路线。
2. 只阻塞该动作及其依赖；独立且已获授权的工作继续，不要求用户批准未知风险来换取进度。
3. 当前 `workflow_gate wait_for_decision` 是板级决策门：只要其他任务仍为 `ready`、`implementing` 或 `reviewing`，工具就拒绝建门，并不判断这些任务是否缺少授权。应先推进独立且已获授权的工作，但这不保证随后一定能建门；不能声称已有逐任务权限等待状态。
4. 多个独立任务都缺授权但仍处于上述状态时，可能已经没有可合法推进的工作，决策门却仍被拒绝。此时 Main 保持相关动作及依赖不执行，汇总全部缺失授权、受影响任务和建门失败原因，直接请求真实用户处理。不能为了满足建门条件而执行未授权动作、虚报任务完成、丢弃必需任务或删除其记录。
5. 只有决策门实际建立后，才使用其真实 decision ID 调用 `resolve`；建门失败时不能虚构 ID。无论用户通过决策门还是直接回答，Main 都需核对授权范围及 `status` 中的其他门；用户回答和 `resolve` 都不自动解除 Supervisor 的独立故障，也不自动满足宿主工具许可。
6. 用户拒绝时，在已批准范围内走可行替代路线，或报告目标无法按原方案完成；不自行扩权，不把被拒绝的必需工作标记完成。

提前预检的作用是减少这类情况，而不是删除这条安全兜底路线。

## 8. 当前版本可以直接采用的操作模板

以下全部是流程示例，不代表用户现在批准了这些操作，也不会由本文启动任务。

### 第一步：用户要求只读预检

```text
先只读分析目标，给出方案 P1、验收标准和需要额外授权的操作清单。
列明必需项、可选项、作用范围、风险、替代方案和重新确认条件。
不要实施，不安装依赖，不启动子代理或 workflow，不提交、推送、发布或部署。
等待我确认方案和授权范围；确认后仍不要实施，等待我发送 supervise 启动命令。
```

### 第二步：Main 汇总，用户给出明确结论

假设方案 P1 可以在无新依赖的路线下完成：

```text
确认方案 P1 和以下授权；本回合不实施，等待我用 /task-supervisor supervise 正式启动。
允许 A1：仅修改当前已明确仓库内的相关源码和测试，不修改凭据或用户配置。
允许 A2：运行已确认不触及真实外部系统的本地验证。
拒绝可选项 A3：新增依赖；采用 P1 中的无新依赖路线。
不允许子代理、workflow、提交、推送、发布或部署。
如果发现 A3 变成必需项，或上述范围发生变化，先说明影响并重新询问。
```

如果拒绝的是必需项，先修订方案并取得明确确认，不直接进入第三步。

### 第三步：用户启动已确认的目标

该模板适用于新/干净会话，或经 `status/tasks` 核对已满足第 4.4 节启动前提的旧会话。存在未停止目标、旧 `done` 任务或未解除人工门时，先明确处理路径，不直接照抄启动命令，也不自动清板、删除证据或解门。

```text
/task-supervisor supervise 按已确认的方案 P1 和授权范围完成目标及最终验收；保留禁止事项，超范围先询问
```

这里的方案 P1 和批准必须已有真实上下文；仅输入这条启动命令，不能凭空制造此前未发生的授权。

执行期间用 `/task-supervisor status` 查看阻塞与下一步，用 `/task-supervisor tasks` 查看完整任务和证据。普通人工暂停用 `pause` / `resume`；故障恢复和决策解决仍遵守现有规则，不能用来补授权。

## 9. 本地产品化范围及冻结条件

本节原是后续方向，现已由用户真实选择 B 批准本地最小实现。冻结结果见[本地实施契约](./supervisor-permission-preflight-implementation-packet.md)；批准不包含通用权限引擎、宿主权限配置更改、功能提交、发布或安装。

“规划、待授权、已授权、执行”作为独立预检记录阶段，**不改当前 `workflowStatus` 的语义**。代码实施前冻结以下条件；本契约 READY 也不代表功能已经验收：

- 启动 Interface：现有 `supervise` 是否保留立即启动语义，以及新旧会话如何兼容。
- 许可绑定：怎样把真实用户确认绑定到方案、目标、会话、范围和有效条件，而不信任模型自报。
- 状态与日志：复用现有会话持久化，明确部分写入失败、旧日志、撤销、fork 和恢复的拒绝语义。
- 执行拦截 Seam：哪些动作能由宿主实际拦截；提示词或结束时 advisor 检查不能被描述为事前权限强制保证。
- 宿主协作：如何显示仍需独立确认的工具许可；任何权限配置变更都必须另获明确授权。

未能实际拦截 Main 其他工具时，只能称为“授权预检与执行约定”，不能称为完整权限沙箱。调度、委派和写权限仍归 Main 与既有执行器；任务完成及目标接受仍需现有证据门。

## 10. 后续实施的验收矩阵

本表是未来实施的检查要求，**不是已经运行或通过的功能测试**。

| 场景                                               | 必须满足的结果                                                            |
| -------------------------------------------------- | ------------------------------------------------------------------------- |
| 已有明确任务授权，只需可逆范围内工作               | 不制造额外审批；直接进入获准流程。                                        |
| 所有必需额外授权明确且齐备                         | 满足会话和任务板启动前提后启动对应方案，范围内不重复询问。                |
| 旧会话存在未停止目标、旧 `done` 任务或未解除人工门 | 不直接启动新目标；先只读核对并明确处理路径，不自动清板或解门。            |
| 必需授权缺失、未知或被拒绝                         | 不启动原方案；给出阻塞或修订方案。                                        |
| 可选授权被拒绝                                     | 仅在替代路线仍符合批准方案和验收标准时继续。                              |

| 新风险、环境变化或超预算                           | 在受影响动作发生前停止并重新确认。                                        |

| 任务、工具输出、advisor 或子代理伪造批准           | 不更新授权结论，不解除决策或其他门。                                      |

| 预检完成、清单 READY，但没有真实用户批准           | 不把它们当作执行批准。                                                    |
