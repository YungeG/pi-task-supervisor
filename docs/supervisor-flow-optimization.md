## 2. 角色与术语

| 名称               | 责任与限制                                                                                               |
| ------------------ | -------------------------------------------------------------------------------------------------------- |
| 用户               | 给目标、授权范围和真实决策；可以暂停、停止、明确恢复。监督建议不能替代用户批准。                         |
| Main（主 Agent）   | 建计划、领取任务、执行工作、进入任务审查、收集证据并维护主任务板。                                       |
| 任务板             | 会话内的任务、阶段、依赖、人工门、执行引用和完成证据；是现有单一持久化状态来源。                         |
| Supervisor advisor | Main 准备结束时运行的只读检查。给继续建议、暂停或接受整个目标；不直接编辑代码、领取任务或控制外部运行。  |
| 任务审查           | 单项任务的 `reviewing` 状态；不等于一次 Supervisor advisor 调用。                                        |
| 执行引用           | `executionRef = { source, runId }`，标记已有外部运行。它是不透明引用，不证明运行仍存活、成功或已经验收。 |
| 工作批次           | Main 一次领取的任务组。可以只有一项；多项被领取不代表它们已经并行执行。                                  |

这里的 workflow 有两种用法：任务板上的 `workflowStatus` 是板级流程状态；`pi-subagents` workflow 是外部执行编排。二者不能混为同一执行引擎。

| 行为      | 当前实现                                                                                                                                                                                                    | 源码锚点                                                                                                                      |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 启动      | `supervise <goal>` 记录目标、启用任务工具并启动 Main，不必先 `enable`。                                                                                                                                     | [commands.ts](../src/commands.ts)：`supervisorCommand`                                                                        |
| 领取      | `get_ready_tasks(count)` 可领取一项或一批；存在任何 `implementing/reviewing` 任务时拒绝新一批领取。依赖与阶段门仍生效。                                                                                     | [engine.ts](../src/engine.ts)：`claimReadyTasks`                                                                              |

| 当前恢复  | `resume` 只恢复任务板；Supervisor 仍 paused/fault 时不会启动 Main。`recover` 在板级门解决后恢复 Supervisor，并重置 reviews、continuations、stagnant；不重置 usage，也不批准其他操作。                       | [commands.ts](../src/commands.ts)：`resume`、`continueNow`；[supervisor.ts](../src/supervisor.ts)：`recoverSupervisor`        |
| 无进展    | Supervisor 的进展摘要只看任务 ID、状态、完成证据；读取运行状态、generation 变化和工具回执增长都不是任务进展。                                                                                               | [supervisor.ts](../src/supervisor.ts)：`progressDigest`、`prepareReview`                                                      |
| 外部编排  | 针对外部运行，`workflow_gate` 仅绑定/清除精确引用；另支持 `wait_for_decision` 建立用户决策门，不控制外部运行。续跑提示要求检查已有运行、不要启动重复写者；没有内建自动派发、等待、停止或恢复外部 workflow。 | [tools.ts](../src/tools.ts)：`bindExecution`、`clearExecution`；[formatting.ts](../src/formatting.ts)：`formatContinuePrompt` |
| 重启/切树 | 未完成的 active/reviewing 或 pending 监督状态恢复为 interrupted fault，要求显式恢复。原生自动压缩与主动切换会话树不是同一语义。                                                                             | [supervisor.ts](../src/supervisor.ts)：`restoreSupervisor`；[events.ts](../src/events.ts)：`registerSessionHandlers`          |

当前目标接受还要求：全部任务 done、无未解决执行引用、最终验收覆盖整板、任务证据绑定有效且最终验证新鲜。`abandoned`、子代理自报成功或“已派发”都不等于验收通过。

Supervisor 当前限制为 40 次检查、20 次自动续跑、连续三次无任务进展停顿、最多 100 个任务及 500 个宿主回执。正常恢复体验优化不能悄悄放宽这些限制。

## 4. 第一阶段：小范围流程优化

### P1-A：明确批次检查点

目标流程：

```text
用户给目标 → Main 建板/领取当前批次 → 实施 → 任务审查与验证
→ Main 正常结束本轮 → 原生结束检查 → 下一批或真实人工门
→ 最终验收 → Supervisor 接受目标
```

- 在 Main 的执行指引中明确：一个可验收批次完成后正常收束，报告已完成内容和下一步，让现有原生检查运行。
- 不在每个 `tool_result` 后调用模型检查，不用 `abort()` 制造检查点，不添加定时轮询。
- 本阶段保留现有批次领取保护、依赖和阶段门，不引入滚动补位或自动派发子代理。
- 批次结束不等于目标完成；advisor 仍可要求修复证据、继续工作或暂停。
- **能力边界**：指引属于执行约定，不能宣称宿主已经强制 Main 每批停一次。如果需要不可绕过的阶段审查门，必须另行设计可执行接口并审批，不能把提示词当作硬保证。
- 指令不能要求正在等待的外部写者重复启动，也不能要求未完成任务为了“结束一批”而提前标 done。

### P1-B：普通人工暂停的一键恢复

拟议行为：通过一次 `/task-supervisor resume` 恢复经过确认的普通人工暂停；不再要求这类暂停额外调用 `recover`。

| 条件                                                                                                        | 拟议处理                                                             |
| ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 本会话有有效监督目标、板和 Supervisor 均为普通人工暂停、宿主空闲且没有未结算审查/旧继续动作、全部门允许继续 | 同时恢复板和 Supervisor，安排最多一次 Main 继续。                    |
| 决策门、invalid journal、fault、预算耗尽、无进展停顿、中断恢复、状态不一致、completed 或 stopped            | 普通 resume 不得解除；说明需要的真实决策、检查、recover 或重新规划。 |
| 未启用会话、没有 Supervisor 的 board-only 模式                                                              | 保留其独立语义；恢复动作不应创建或启用新的监督目标。                 |
| 旧日志只有文本原因，不能可靠判定暂停来源                                                                    | 保守处理，不凭英文文案或字符串匹配赋予一键恢复资格。                 |

约束：

1. 一键恢复必须由用户显式调用，不是工具、advisor 或子任务完成通知自动解暂停。
2. `reviews`、`continuations`、Supervisor `stagnant`、tokens、cost、mutation epoch、目标和证据绑定保持不变；尤其不能直接复用会清零计数的 `recoverSupervisor`。
3. 人工 pause 不得掩盖此前的 fault、预算或无进展停顿；资格检查必须考虑仍然有效的全部停顿原因和当前限额，而不是最后一条展示文案。
4. 决策门仍由正确的 decision ID 和真实用户回答解决；普通恢复不能批准发布、付费、迁移、部署、清理或其他独立权限。
5. 先验证全部条件再变更。多条 append-only 日志不是原子事务；实现包必须明确提交顺序、部分持久化失败的故障状态及恢复方法，不能留下看似成功的半恢复或静默回放。
6. 取消旧审查/继续票据并等待宿主空闲，拒绝迟到结果；不重启、重复派发或声称已停止外部写者。

实现契约现已冻结在实施包：可选 `holdCause`、强停顿不降级、旧未知原因拒绝快速恢复、先写 Supervisor 再写板日志、提交或派发失败的可见 journalFault。原生 command context 必须提供真实空闲等待，不能依赖 SDK 默认空回调。

### P1-C：状态说明“谁负责、为什么等、下一步是什么”

复用现有 snapshot、Supervisor 状态和宿主可确认的信息，不新增第二个任务状态库。

建议状态信息包括：

- 当前目标和任务计数，当前领取的任务组；没有正式批次 ID 时不虚构 ID。
- Main 是否正在运行（仅在宿主能确认时显示）、任务已领取还是正在任务审查、Supervisor 是否正在检查。
- 下一次计划检查点；它是执行约定，不是已实现的强制调度保证。
- 所有阻塞原因及实际可用的人类命令；不能只显示一个最高严重度原因，然后推荐一个被其他门拒绝的命令。
- 自动检查/续跑计数与限额；这些不是用户手动 resume 次数，也不是 Main 的全部模型用量。
- 有执行引用但缺运行证明时显示“已有运行引用，状态待核查”，不能仅凭 `runId` 显示“仍在执行”。

保持现有八行板上限及完整只读列表。用户查看状态不应启用工具、产生模型调用、改变 task/goal 或安排继续运行。

## 5. 第二阶段：既有异步执行器衔接（范围已收缩）

用户明确排除了 Supervisor 自建并行调度与写权限管理，并要求继续本地开发。符号级契约见 [异步衔接实施包](./supervisor-async-integration-packet.md)。保留 `claimReadyTasks` 的 active-task 保护；Main 和既有执行器继续负责调度。

### P2-A：区别“等待已有运行”和“无进展”

- 只有外部执行器提供的、关联本会话和精确运行身份的可核验运行状态，才能建立等待；单凭 executionRef、模型文字或反复读日志不够。
- 使用执行器已有完成通知唤醒 Main，不反复派发 advisor 检查，也不将可靠等待机械计入“三次无任务进展”。
- 等待必须有明确期限或可核验的有限存活策略。未知状态、超时、丢失回执或失败不能无限续期或重置预算。
- 通知投递/去重/唤醒继续由执行器负责，Supervisor 不复制通知处理器。只在原生边界核对 owner 的当前会话结构化状态、有效上下文和精确绑定运行；原始旧/重复/外来通知不直接改变等待或人工门。
- 用户 pause/stop、决策、fault、预算停顿优先于自动唤醒。完成通知可以保留结果，但不能解除人工门。
- 完成后由 Main 收集结果、核对引用、清除已解决运行引用，再取得新鲜宿主验证证据；通知本身不能把任务标 done。
- 重启后不能默认任务仍活着、默认失败或自动重派。先核实运行身份和现状，再走显式恢复；未知执行状态要保留并可检查。

### 原 P2-B：不纳入本轮 Supervisor 范围

派发、并发上限、滚动领取、子代理写权限和 worktree 隔离归 Main 与 `pi-subagents`/workflow，Supervisor 不重新实现。Main 仍是主任务板写者；执行成功、审查通过、任务完成和目标接受仍须分别判断。父 workflow 完成但结构化子节点仍 active 时不能当成整个执行完成。子引用不自动猜测父身份；失败不静默转 CLI，不自动重派、合并、提交、部署或清理。

## 6. 不可削弱的保护

- 会话默认未启用；目标、运行引用、任务和证据保持会话隔离。
- pause、decision、fault、stop 的门不能被 advisor 建议、外部完成通知或普通恢复隐式批准。
- 已完成的受监督任务保持冻结；必需任务不能被丢弃或 abandoned 后算作成功。
- 宿主验证仍要求精确任务审查和 epoch；旧成功、纯文本 exit code、模型自报结果不能补成新证据。
- 接受目标仍检查全部任务、最终依赖覆盖、未解决运行引用与新鲜最终验证。
- 保留原生自动压缩、重试、队列和 `agent_before_settle` 的正确顺序。通知型 `agent_settled` 不成为新的派发点。
- 不恢复已移除的 `pi-context` 依赖，不把内部 abort 一律当成可自动放行，也不让重启/切树自动重放未完成监督。
- 任务门不是 OS 沙箱；Main 的其他工具权限仍由宿主负责，不能把本提案描述为全面阻止所有外部副作用。
