# Supervisor 集中审批流程修复计划

日期：2026-10-27。源码核对基线：`0f8f5f83e01a9db1d1e2c4662046471797897ab0`。

**本次只形成修复文档，不施工。** 目标方向已确认，但联合确认、前置定义绑定和验收接入的关键技术规则尚未冻结，不能直接交给写代码的执行者临场选择。本文为**目标与修复范围草案**，不是新功能已实现、已验收或获得施工授权。施工节点的技术就绪状态只在下述施工索引维护，本计划不独立维护另一份进度状态。

施工细化、真实依赖 DAG、并行边界及分项卡见[施工索引](./supervisor-approval-workflow-implementation/README.md)。节点状态、排程和文件归属只在该索引维护；本计划的 R0–R5 保留为范围与完成判据对照，不是另一份进度表。新增施工拆解尚未独立审阅，不把旧计划审阅结论扩展为其接受。

## 一页摘要

**要修成什么**：用户在执行前看懂完整材料，尽量一次集中确认；系统判断当前范围确实可执行后，用户独立 Start；范围内自动推进，只有真正的新决定才打断。

**不只是换 UI**：同时修复执行前准备、确认协议、启动／恢复资格、正式验收接入、异常恢复，以及真实端到端验证。UI 采用已认可的单列审核单方向，不替代这些行为规则。

**必须保持**：权限、验收定义、首次启动和结果通过分别有据可查；不重复批准或派发；不因恢复清预算；不因追求一次审批放开未知风险。

**目前谁做什么**：本轮由 Main 记录计划并检查文档。后续若进入实施，Main 先收敛第 3 节的技术契约，再由单一写者修改已冻结范围。技术证据和接口问题由执行方查清，不要求用户点“同意”替代；现在没有需要用户补批的技术细节。

**明确不做**：本轮不修改源码、测试或配置，不安装／重载、不操作正在使用的业务会话，不提交、推送或发布。历史恢复体验候选不因此自动合入主线。

## 1. 依据与完成标准

- **C1｜用户要求**：执行前盘点可预见权限，尽量集中审批；每个用户可见步骤给出下一步；决策材料和审核 UI 要清楚易用；当前只记录设计，不施工。
- **C2｜流程设计**：[集中审批与审核前移设计](./supervisor-consolidated-approval-flow-design.md)规定权限复用、规则前置、产物事后核验及准备阶段的边界。
- **C3｜原预检原则**：[原预检设计](./supervisor-permission-preflight-design.md)要求范围内不重复询问、必需项缺失不执行、超范围仍需确认。
- **S1｜现有安全与兼容行为**：真实原生回应、物理见证、精确 owner／版本、现有暂停／撤销／未知执行门、预算及旧记录语义继续有效，不能以模型文本、报告或 UI 状态替代。
- **E1｜已有独立审阅**：此前流程图的结论为 `OK with notes`，指出前置绑定、联合确认半写恢复和下一步资格三项缺口；它不是本计划或产品代码的独立验收。

最终应证明：正常场景不再出现“批准并 Start 后，才补本可提前准备的审核”；创建检查器或新产物的正常任务不会陷入启动死锁；审批、执行、恢复和结果判断均对应正确目标及版本；界面能明确说明当前状态和合法下一步。

## 2. 缺口、现状证据与修复方向

| 缺口                           | 已确认的现状／尚未闭合的规则                                                                                               | 修复方向                                                                                             |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 执行前准备未形成闭环           | `submitAndPresentPreflight` 提交后即进入权限确认；`preCompileOwner` 却要求已 active 的执行 owner，产物捕获要求实际文件存在 | 先明确当前可审材料与待准备事项，拆开定义确认、执行身份关联和产物版本取证                             |
| 一次确认的联合协议缺失         | 权限和合同采用不同原生确认与记录路径，现有业务“允许”不能直接当成合同定义回应                                               | 为同一版完整材料规定联合身份、准确选择和分别留证；必要事实不齐不开放相应执行                         |
| 就绪与下一步不一致             | 通用提示可能推荐执行或审核，但合同门或暂停状态仍会拒绝；不能只用“paused→recover”概括所有原因                               | 复用真实资格依据，区分未就绪、用户暂停、技术故障与未知执行，提供可执行且带准确参数的动作             |
| 正式验收接入不覆盖所有实际场景 | 当前 `run_check` 是有限 Node 只读检查，不能直接等同任意 Python／Bash；合同路径也受当前 workspace 范围限制                  | 明确受支持的执行／证据路线，优先解决外部守卫与 Python 测试的代表场景，不伪造支持或统统改成人工总确认 |
| 新联合流程的恢复与兼容未闭合   | 原生见证、投影修复、防重复 Start 等已有实现，但尚未覆盖新联合事实及前置绑定                                                | 将 reader、半写、重开、切树、撤销和未知派发与新协议一起设计、实现和验证                              |
| 缺少真实新流程验证             | 目前有设计、代码核对、官方 UI 调研和 HTML 原型；没有新联合审批的真实终端执行链                                             | 用同一冻结候选完成隔离的正常／异常链路、兼容及真实 CLI／PTY 验证                                     |

“新流程未闭合”不等于现有防护全都缺失。应复用现有 Module 和控制记录，不重写整个 Supervisor。

## 3. 实施前由 Main 冻结的技术契约

以下不是交给用户反复审批的事项，也不是授权 writer 自选架构的空白。Main 应结合源码、必要的隔离小样本和已有约束给出明确结果；当前仍未完成。

1. **前置确认与执行身份**：确认发生时绑定哪个真实规划／目标来源，Start 后怎样精确关联到本次执行；新产物缺失不阻断规则确认，缺失必需输入仍明确阻塞。
2. **联合确认协议**：同一次原生操作具体证明哪些权限选择、哪版定义和范围；记录 schema、digest、原始回应与见证、写入顺序及容量预算怎样对应。不能简单复用旧业务回答，或提高上限、裁掉条件来凑成一包。
3. **确认失效边界**：方案／检查定义实质变化、普通源码进展、产物版本变化分别影响什么。业务权限复用不等于旧测试结果复用，也不能把旧版确认挪给新版材料。
4. **准备阶段与就绪资格**：检查器尚需本任务创建时，哪些获准准备动作可以先做、受哪些验收约束；何时冻结具体检查定义；不得把所有未来检查器存在作为统一 Start 前提，也不得用准备阶段绕过权限。
5. **有限验收与证据接入**：Python／外部产物采用什么受支持路径，真实宿主执行、close／exit、owner、产物版本和结果语义怎样闭合。Main 能通过现有工具运行 Python，不等于其任意报告已是可信正式验收。
6. **恢复与兼容**：各保存点失败的结果、能否精确修投影、何时必须保留未知；新事实的旧 reader 拒读／兼容办法、旧目标的保持规则，以及已记录 Start 不重复派发的证据。

实施包还需明确 symbols、调用方、精确写集、单写者和可失败的验证。以上关键项未冻结时保持 `NOT_READY`，不能仅凭新的用户批准把技术缺口改成 READY。

## 4. 修复顺序与每阶段产出

下表按修复范围和退出条件分组，**不是新增一串用户审批门，也不表示所有分组必须严格串行**。实际依赖和可并行节点以[施工索引](./supervisor-approval-workflow-implementation/README.md)为准。以后若获得同一明确范围的实施授权，范围内可以连续推进；新增权限、风险或其他显式保留事项才另行确认。

| 阶段                          | 交付与依赖                                                                           | 退出条件                                                                           |
| ----------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| R0 技术契约收敛               | Main 完成第 3 节的身份、行为、失败及兼容决定，形成适量的实施包                       | 写者不必猜联合协议、准备范围或验收来源；材料／写集／首个用例明确                   |
| R1 就绪与诊断统一             | 先改善当前可确认的只读状态、字段错误和合法动作顺序；新协议相关部分依赖 R0            | 不推荐必定被另一门拒绝的动作，不以通用 recover 替代诊断，参数完整                  |
| R2 前置定义与联合确认最小闭环 | 实现集中材料、一次明确确认、定义前置、Start 关联；同时实现对应 reader 和必要半写恢复 | 正常链路可达；部分保存不执行；不跨版本赋权，不重复批准或 Start                     |
| R3 有限验收接入               | 依 R0 选定路线接入代表性外部守卫／Python 场景；需要时最小扩展，不默认新增通用执行器  | 真实执行与证据可核验；缺失或不支持明确失败，不能以人工“通过”掩盖应由程序证明的事实 |
| R4 原生审核 UI 与材料         | 将单列稿接入 R1／R2 的实际状态和 R3 的能力边界，复用现有 TUI 与原生回应路径          | 主视图与完整材料一致；草稿／确认／启动／验收不混淆，确认后有准确下一步             |
| R5 整合验证与接受             | 对同一冻结候选完成第 6 节验证及获准的独立审阅，Main 复核结果                         | 必需用例和兼容通过；失败、未知与范围明确，不以演示、设计审阅或部分通过冒充完成     |

R1 中不涉及新权威的诊断改进可以独立准备，不必等其他模块全部完成；它不能在新协议未实现时提前显示“联合确认已完成”。R2 的恢复 reader 不是可留待上线后补做的工作。每阶段通过也不自动授权安装或业务执行。

下列是已定位的影响面，**不是允许任意修改全部文件的最终写集**。实施前须按实际契约收敛到具体 symbols 和调用方。

| 影响面         | 现有入口／位置                                                                                                                                                                         | 主要责任                                                               |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 预检与原生权限 | `src/preflight.ts`、`src/preflight-human.ts`                                                                                                                                           | 提案、准确选择、有效批准、独立 Start 及已有投影恢复                    |
| 合同与版本     | `src/acceptance-runtime.ts::preCompileOwner/prepareContractBinding/contractCompilationAdmission`；`src/acceptance-proposal.ts`、`src/acceptance-journal.ts`、`src/artifact-version.ts` | 定义确认、精确来源、版本及新增事实恢复，不把产物事实提前               |
| 流程资格与控制 | `src/flow.ts::nextFlowStep`；`src/commands.ts`、`src/events.ts`、`src/supervisor.ts`                                                                                                   | 显示与执行使用一致资格，保持暂停／撤销／未知执行及原有监督约束         |
| 正式检查       | `src/check-runner.ts` 及合同的证据消费路径                                                                                                                                             | 有限执行和真实结果，不把报告 DTO、复制的退出码或任意命令当正式证明     |
| 原生 UI 与材料 | `src/human-ui.ts`、`src/human-presentation.ts`、`src/human-decision-card.ts`、`src/human-material-view.ts`、`src/human-scope-view.ts`                                                  | 可读材料、草稿选择、焦点、滚动和反馈；保留原生回应与完整核对的信任保证 |

保持以下行为：

- Main 负责技术契约与最终接受，共享文件保持一个写者；本轮不启动 writer 或新建 worktree。
- 不新增另一份任务板、权限真相或全局恢复调度器；只读状态／渲染不做授权采用、全量历史重扫、进程派发或结果认证。
- 保留原生不透明回应、物理见证、实际分支／owner 与当前性检查；浏览器预览、普通 SDK UI DTO、工具输出和模型文字不能批准。
- 不能为合并审批静默扩大文件读取范围、工具白名单、账号权限或 shell／子进程能力。
- 用户 pause／stop／revoke、其他 owner 的 hold、累计用量与已耗预算不被审核、修复或恢复顺带清掉。
- 实施契约明确覆盖旧记录、旧宿主与现有入口；不把历史 legacy 记录偷偷升级为新审批证明，也不只凭当前机器的 SDK 文档宣称所有版本兼容。
- UI 原型不是可直接复制上线的实现；窄终端、中文宽字符、按键、主题和审核区域须实际验证，不承诺网页像素级外观。

## 6. 验证安排：先最小红灯，再验证整条链

以下均为后续计划，**本轮未新增测试代码或执行产品测试**。所有运行验证使用隔离、可控的会话与临时数据，不借用户正在使用的业务会话试错。

### 首个代表用例

使用已有可核验检查器和一个尚未生成的正常输出：在首次 Start 前确认权限与检查定义，Start 后才创建产物并取得实际验证证据。

当前入口依赖 active owner，且产物捕获要求实际文件存在；该用例应能明确暴露现有前置绑定问题。先观察对应失败，再证明新路径能通过，并证明启动前没有出现产物通过证据。不能只测一个绕过真实门的浅层 helper。

### 第二个必需正向用例：在本任务中创建检查器

固定用例的同一明确目标和已批准范围同时覆盖准备及后续工作，准备完成后没有新增业务权限。必须按 R0 冻结的真实路线贯通：

```text
合法启动获准准备 → 实际创建检查器 → 按契约冻结具体定义
→ 继续依赖该定义的后续工作 → 取得实际产物与真实验收证据
```

不能只证明准备工作不越权，还要观察准备结束后的定义绑定、继续执行和验收结果均可达。若准备任务已编译／推进，不能仍被旧的“仅编译前绑定”门永久卡住；也不能通过绕过门、重建同一目标、重复 Start，或提前执行依赖未冻结定义的工作来使测试通过。

具体新定义如按契约需要真实确认，应准确说明确认对象并取得该确认，不能自动信任刚生成的代码；这不等于重复审批未变化的业务范围。仅因阶段名称改变，不应重新收取业务授权或首次启动意图。

### 按风险分配的检查

- **集中材料与版本**：部分批准／必需项拒绝／未知事项、材料修改、过期确认、全部关键范围完整呈现；正常代码进展不重批权限但旧验证结果不可冒用。
- **准备阶段**：本任务创建检查器时仅执行已获准的准备范围；未获准或没有独立合法路线时停住，不把未来检查器当受信事实。同时必须通过上述创建、冻结、继续到验收的正向贯通用例，不能只测阻塞负例。
- **保存与重开**：在原始控制、见证、两类事实、投影、Start 记录和派发各处注入失败；覆盖切树、撤销、用户暂停及未知执行，验证不重问、不补批准、不重复派发。
- **资格一致性**：权限已批但定义未绑定、暂停且合同未绑定、多个门并存、已确认但投影缺失；推荐动作实际合法，或准确说明为什么没有合法动作。
- **正式验收**：至少一个有代表性的外部守卫／Python 场景；实际来源、scope、版本、close／exit 和结果语义可追溯。未接入的必要能力仍是失败／缺口，不能算修复完成。
- **真实界面与兼容**：CLI／PTY 中跑新流程，覆盖窄／宽窗口、中文长材料、取消、焦点与过期；验证已声明支持的宿主及旧记录。自动按键不是人类身份或真实用户可用性接受。

优先扩展已有 `preflight-*`、`acceptance-*`、`flow-commands`、`human-*`、`check-runner*` 和 `restore-*` 测试，不建立第二套测试系统。小样本通过后再跑相关集成与既有必要完整门；同一冻结候选集中做最终验证，避免每阶段重复全量运行。任何必要门失败或无法运行都明确记录为失败／缺口。

最终独立审阅检查新确认的权威、版本、失败恢复、兼容、验收来源和 UI 完整性；仅在获准的委派方式下运行，不复用旧图审阅冒充实现审阅，也不因工具失败静默改用其他执行方式。

## 7. 整体完成判据与交付边界

只有同时满足以下条件，才能宣称本范围修复完成：

- 正常路径达到“完整材料 → 集中确认 → 当前范围就绪 → 独立 Start → 自动推进与验证”，没有原先可避免的事后补手续。
- 新产物／待创建检查器不会造成无条件启动死锁，且没有因此放开未授权或无验收依据的工作；任务内创建检查器的正向链路已按第 6 节贯通验证，不只证明准备阶段可以开始。
- 联合确认与原始见证、owner、版本和执行身份闭合；必需事实缺失不执行，半写及恢复不重复批准／派发。
- 每个用户可见步骤都有明确结果和合法下一步；技术故障不被包装成新的业务审批。
- 代表性实际任务能通过受支持的证据路径完成验证；没有用“人工总确认”掩盖必需的自动事实缺口。
- 原生 UI、旧记录、宿主兼容和必需验证通过；未完成的真实用户验证、未支持能力与剩余风险单独列出。
