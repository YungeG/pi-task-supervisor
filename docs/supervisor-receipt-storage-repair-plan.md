## 1. 结论与目标

**推荐取消“同一目标累计 500 条回执即故障”的机制，改为：Pi 会话日志保存追加式证据，Supervisor 保存小型检查点，运行时使用有界缓存。**

缓存回收不等于删除证据；缓存未命中不等于证据失效。任务完成和最终验收仍必须查到当前分支上的真实宿主回执，满足既有身份、审查、版本和退出码要求。

本方案要交付的用户结果：

1. 正常长任务经过第 500、501、1000 条工具结果时，不因历史条数暂停，也不要求清空任务板。
2. 先前完成任务绑定的旧证据，即使退出缓存，仍能验证；当前审查中尚未绑定的有效证据同样不能因缓存回收而丢失。
3. 压缩、重启、树分支切换后，证据身份与有效性不变；其他会话、目标或分支的证据不能借用。
4. 写入失败、半写入和未知执行结果必须可见，不能让旧验证在未知修改后继续被当成“新鲜验证”。
5. 证据增加不再导致每条回执反复重写此前全部回执；内存缓存有明确边界。

**不承诺“无限任务零成本”。** Pi 自身的会话日志和恢复成本仍随历史增长。本次消除的是插件自行制造的累计条数死锁和全量回执重复写入，不改造 Pi 的底层会话存储。

## 2. 已确认的现状与缺陷

以下是基线代码事实，不是对原作者动机的推测：

| 现状                                                                      | 位置                                       | 后果                                                       |
| ------------------------------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| 持久化 Schema 将 `receipts` 限为 500 条                                   | [supervisor.ts](../src/supervisor.ts#L97)  | 不能只改运行时判断，否则恢复仍拒绝新状态                   |
| `observeTool` 在追加前检查 `length >= 500`                                | [supervisor.ts](../src/supervisor.ts#L327) | 第 501 个符合记录条件的结果不能成为新回执                  |
| 除任务工具、`submit_preflight` 和重复 ID 外，读取、搜索、失败结果等也记录 | 同上                                       | 500 并不等于 500 次验证或 500 个任务                       |
| 上限检查早于 mutation epoch 更新                                          | 同上                                       | 工具已经执行，触顶时却可能没有记录这次修改或其版本变化     |
| `tool_result` 捕获异常后将 Supervisor 置为 fault                          | [events.ts](../src/events.ts#L510)         | 是执行后的监督故障，不是执行前阻止工具，也不回滚工具副作用 |
| 每次 `saveSupervisor` 都追加整个状态，含全部回执                          | [supervisor.ts](../src/supervisor.ts#L152) | 单条回执会在后续快照中反复出现；长期运行的累计写入成本偏高 |
| `recover` 保留回执，恢复也读取相同历史                                    | [supervisor.ts](../src/supervisor.ts#L257) | 触顶后恢复不能释放容量，下一条结果仍触顶                   |
| advisor 只选绑定证据和最近 30 条，另有 64,000 字节限制                    | [supervisor.ts](../src/supervisor.ts#L502) | 500 条存储上限与模型输入上限不是一回事                     |

因此不能只删一行判断、把 500 改成 5000，或让 `recover` 清空数组。

## 3. 不变条件与排除项

### 3.1 必须保持

- 只有真实宿主工具事件能产生证据；Main 自报路径、状态或退出码不能冒充回执。
- 保持对外引用 `tool:<toolCallId>`，不要求用户或任务完成证据改写 ID。
- 保持任务审查身份与 task digest 校验；命令证据必须具备宿主结构化 `exit_code: 0`。
- 验证不能跨潜在修改继续有效；最终验收需要当前版本的新验证。
- 已完成任务的 bindings、任务板依赖闭包、预检授权和撤销约束不因存储迁移而放宽。
- 未解决的执行引用、人类决策、暂停、真实中断仍遵循现有流程，不能重复派发执行。
- 继续保持 100 个受监督任务、40 次检查、20 次自动续跑、三次停滞限制，以及现有显式恢复语义。缓存回收不得重置这些预算、tokens 或 cost。
- advisor 的 **64,000 UTF-8 字节**上限与完整受保护证据不缩短原则不变；完整 preflight 证据仍受保护。
- 继续脱敏，并保持现有单条 input/output 摘录约束；不能为保存更多历史而写入原始凭据。
- 当前分支是读取依据；fork 不继承授权，树切换不复用另一分支的缓存结果。

### 3.2 本次不做

- 不增加 SQLite、数据库、后台归档进程、自动删除/TTL 或独立 sidecar 文件。
- 不扫描全机 session 目录，不修改旧 journal，不重建已经丢失的“成功证明”。
- 不把工具执行时间、业务权限或任务真实性交给缓存策略判断；本扩展仍不是 OS 沙箱。
- 不提高模型包大小、任务数量或自动续跑预算，不取消审查与最终验证。
- 不自动重开 faulted completed board，不清空已验收任务，不借迁移消除旧告警。
- 不在本轮提交、推送、发布、安装或重载业务会话。

## 4. 选型

| 方案                                               | 判断                                                               |
| -------------------------------------------------- | ------------------------------------------------------------------ |
| 提高/配置累计上限                                  | 仅延后同类故障，仍有全量快照重复写入，不作为正式修复               |
| FIFO 删除 `state.receipts` 中的旧项                | 会破坏绑定或尚未绑定的审查证据，拒绝                               |
| 只保留绑定项和最近若干项，无历史读取路径           | 当前审查尚未提交的回执可能被回收，拒绝                             |
| 复用每一个旧 Supervisor 全量快照作为新格式永久归档 | 旧记录可作兼容锚点，但新记录继续如此写入会保留主要存储问题，不推荐 |
| **追加式回执日志 + 小检查点 + 有界缓存**           | **推荐**；复用 Pi 的树状会话日志，无新外部存储依赖                 |
| 独立数据库/侧文件                                  | 增加多文件提交、移动会话和 fork 一致性问题，当前无必要             |

这里的“归档”只是把持久化证据与运行缓存分开，**不是把旧回执移动出当前分支或删除**。

## 5. 目标结构与小型 Interface

新增一个内部 Module：`src/receipt-store.ts`。它承担身份、追加/读取、恢复与缓存；不建立可插拔存储框架，不为单个实现增加 factory 或 adapter 层。

建议对外只暴露四类操作，实际 TypeScript 签名在实施前冻结：

1. `prepareToolCapture`：在 `tool_call` 捕获当前审查身份；潜在修改工具先记录执行意图。
2. `commitToolReceipt`：在 `tool_result` 保存真实结果，返回已确认的回执；只确认成功的持久化闭包。
3. `readReceipts`：按引用批量解析当前分支证据，或选择最近窗口；缓存未命中时读日志，不返回伪造占位证明。
4. `restoreReceiptStore`：从当前分支、检查点及兼容锚点恢复账本头、版本和缓存视图。

`assertObservedEvidence`、`acceptanceError` 和 `evidencePacket` 保留各自业务责任，只改为通过同一读取路径取得回执。禁止分别实现三套缓存回退逻辑。

### 5.1 三层数据

| 层                            | 内容                                                                                    | 淘汰规则                                               |
| ----------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Pi 自定义日志                 | 每个真实回执一次；潜在修改调用的意图及中断处理记录                                      | 本次不删除、不改写                                     |
| Supervisor 检查点             | 目标身份、账本头、epoch、计数、bindings、未闭合 intent 引用、原有控制状态及可选兼容锚点 | 不嵌入整个历史回执数组                                 |
| extension-instance-local 缓存 | 最近/常用的回执，来自已验证日志                                                         | 可按数量与字节淘汰；不改变日志、bindings、epoch 或权限 |

bindings 保留其任务 digest 和精确 refs；**绑定证据的持久化记录不可淘汰，但它的内存副本无需永久 pin 住**。取用时必须能从日志重新解析。

### 5.2 身份与格式

冻结方案原建议 Supervisor checkpoint schema v2、回执日志独立 schema v1。G0 已确认并行候选占用 v2，因此本候选改用 **v3 检查点 + v1 receipt-ledger**；不覆盖/混认其未提交 v2。其余身份与恢复要求不变。

- 保持现有 `continuous-tasks:supervisor` 检查点类型，以便旧代码遇到 v2 时明确拒绝，而不是误当作无监督状态。
- 新增一个 `continuous-tasks:receipt-ledger` 自定义类型，用 `kind` 区分 `intent`、`receipt`、`close_unknown`。
- 新目标分配独立 `goalId`；读取作用域是 `(sessionId, goalId, 当前分支)`，不能用目标文字相同代替身份相同。
- `toolCallId` 作为宿主不透明 ID 原样保留，支持 Pi 1.2 的嵌套调用 ID；不能假设所有子调用都有独立 transcript message。
- 日志记录携带单调 `ledgerSeq`、前一账本 entry ID 和作用域；检查点保存账本头。序号统计日志事件，不冒充工具次数。
- `receiptCount` 单独累计真实回执数量，仅用于诊断，不是新的停机上限。
- 现有宿主结果 digest 与 task review digests 保留；日志结构校验不等于证明工具输出的业务真实性，也不构成对手工改写磁盘的 OS 安全隔离。
- `ledgerSeq`、epoch、计数必须是安全整数；冲突 ID 或非单调记录不得覆盖已有证明。

### 5.3 写入与 epoch 顺序

潜在修改包括未知工具；只读判断沿用现有白名单和 `readOnlyHint`，不能因工具名字看起来像读取而豁免。

```text
tool_call
  → 先应用现有任务/授权门
  → 捕获调用开始时的 task review digests 与当前版本
  → 潜在修改调用：追加 intent，确认当前分支可见
  → 失效旧新鲜验证，登记进行中的修改，再允许该工具执行

tool_result
  → 从宿主事件读取结果、结构化退出码；脱敏
  → 匹配调用上下文/intent，追加 receipt，确认当前分支可见
  → 闭合对应 intent，发布运行时视图并更新缓存
  → 返回原始结构化结果与真实回执 ID
```

关键约束：

- 潜在修改 intent 成功后即推进因果版本；结果不能因为缓存满或落盘失败而把版本退回。epoch 是版本，不是账单计数。
- 普通单次修改调用只推进一次；嵌套/交错执行需要保守失效规则。未知父调用闭合可能包含未被子事件覆盖的修改，不能仅因子命令成功就认定其证明仍新鲜。
- 不允许在其他潜在修改尚未结束时完成验收；与未结束修改交错的命令不能作为最终验证，需在结束后重新验证。
- 不把尚未开始审查时启动、在审查中才返回的命令变成该审查的证明。
- 这些保守规则必须在实施前覆盖串行、并行及嵌套事件测试；没有宿主 parent ID 时不得凭字符串猜父子关系。
- intent 不能确认写入时，可见阻止这次受监督工具调用并置日志故障；这是记录能力的技术门，不是新增业务权限引擎。
- 工具已经执行而 receipt 写入失败时，不声称回滚；保持未知结果、旧证明失效和监督停顿。不能自动重试原工具。
- 采用当前 preflight 的“append 后确认真实 entry/leaf”原则，但不照搬每次全量 `getBranch()` 的查找：写前记住 leaf，写后通过公共 `getLeafEntry()` / `getEntry(id)` 检查真实类型、完整数据、作用域及直接 parent；生命周期恢复时建立当前分支的可信头，后续增量延伸。Pi 1.1/1.2 的公开 Interface 均有这些读取方法。不能每条结果全扫描历史，也不能仅凭缓存声称记录仍在当前分支。
- 只使用 SDK 公共 Interface；**不额外宣称实现了 SDK 未保证的 fsync 或断电原子性**。

只读工具仍产生可追溯回执，但不推进修改版本。若结果缺少调用开始上下文，不得把它升级成可用于验收的新证明。

### 5.4 检查点与崩溃恢复

不再每条结果调用“含全部回执的 `saveSupervisor`”。回执追加为增量；目标、任务绑定、检查、暂停和恢复等状态变化继续写小检查点。

- 恢复按 `getBranch()` 的路径顺序验证检查点和账本，应用检查点之后的增量；不能只读取最后一个检查点而忽略较新的 intent/receipt。
- 检查点引用的账本头必须在当前分支真实存在，前驱和作用域一致；其 epoch、回执计数和未闭合 intent 引用必须与该头之前的账本一致，不能用新检查点掩盖更早的未闭合捕获。漏记录、冲突或无效自有记录均不能静默跳过。
- receipt 已提交、后续检查点尚未写入时，重放该 receipt，不重复计数、不重新执行工具。
- intent 存在但没有结果时，状态是“执行结果未知”，不是成功、失败或未执行。禁止验收和自动重放。
- 用户显式 recover 前仍需等待宿主空闲、处理原有 board gate、检查已有执行。合法 recover 可写 `close_unknown`，仅记录该捕获已按未知结果处理；不能伪造成功 receipt。
- 恢复后必须失效缺口前的新鲜验证，重新取得验证。已经完成任务的历史 binding 不被删除，也不免除新鲜最终验证。
- 迟到结果不能闭合已经人工处理的旧捕获、污染新目标或新分支；必须按身份拒绝或隔离并可见提示。
- `completed` 之后出现潜在修改 intent，必须使既有接受失效，即使在结果写入前中断，也不能恢复成仍然接受。
- 上述重放不自动触发 Main；保持现有中断后显式恢复原则。

## 6. 缓存、查询与容量

### 6.1 有界缓存，不再有累计条数死锁

建议在现有 `continuous-tasks.json` 增加可选对象：

```json
{
  "receiptCache": {
    "maxEntries": 128,
    "maxBytes": 1048576
  }
}
```

- 这是**缓存**预算，不是目标回执总数预算；128 或 1 MiB 被达到时只做缓存回收，不暂停 Supervisor。
- 字节按序列化缓存项的 UTF-8 字节计算，不用 JavaScript 字符数。两种限制同时生效。
- 单条大于缓存预算：不放进缓存，通过已验证日志读取；不能丢弃这条回执或把它判作失败。
- 建议有效范围：`maxEntries` 为 1–4096，`maxBytes` 为 16 KiB–64 MiB；缺省使用上例。非法值不接受为无限预算，按现有保守配置策略报告/回退。
- 缓存量不足、配置变小、缓存淘汰均不改变权限、任务状态、证明有效性或自动执行预算；配置变大不新增授权。
- 这些默认值是初始工程预算，**不是性能达标结论**；实施阶段用小样本后逐级放大的试验核对。

advisor 仍选“绑定证据 + 最近 30 条”，不能因缓存恰好只有 10 条而只发送 10 条，或把缓存大小误当作模型包大小。

### 6.2 不让查询重新变成二次方问题

- 同一次完成校验/验收批量解析所需 refs，一次分支扫描中收集；禁止每个 ref 单独遍历完整 branch。
- 常规命中缓存时，不因一次读取重放整份历史；但缓存必须验证其当前分支来源，树切换/会话恢复后清空或重新建立可信视图。
- 不新增永久保存全部历史回执副本的无界 Map；会话历史由 Pi 管理，插件只保留有界缓存和必要的控制元数据。
- 构造 advisor 包时保持现有可缩短/不可缩短界限。完整保护材料超 64,000 字节仍可见拒绝，不截断绑定证据以换取通过。
- 写入增长验收应固定任务数、bindings 与单条回执大小，单独测本扩展新增记录字节；不能把 Pi 原有 transcript 大小算作本修复成效，也不能宣称任意增长的任务板都是常数成本。

## 7. v1 历史兼容与已经触顶的目标

### 7.1 读取与迁移

1. 保留严格的 v1 读取器；旧格式仍按其原有最多 500 条验证，不能借迁移接纳畸形旧记录。
2. v1 的 status/查看历史只读，不批量重写全部旧快照；新目标直接使用新格式。
3. 未完成的 v1 目标在用户显式 recover、通过既有控制检查之后迁移。自动恢复不得替用户解除暂停或预检撤销。
4. 用当前分支最后一个有效 v1 检查点作 `legacyBase`，保存其 entry ID 与数据 digest。其完整回执数组作为只读基底，避免把旧日志重新写入 500 次。
5. 迁移的稳定目标身份从当前会话和这个精确兼容锚点派生；后续 v2 检查点始终引用同一锚点，不能按 goal 文字合并其他目标。
6. 继承 bindings、旧回执 ID/digest、目标/model、tokens/cost 和 preflight binding；升级格式本身不重置审批或执行预算。合法显式 recover 的原有计数重置单独按原规则执行。
7. 迁移活跃/未完成目标时推进 epoch，要求新验证。尤其已有 500 条时，不能假定触顶期间没有漏记修改，也不能把旧“成功”重新解释成新鲜验证。
8. 确认 v2 迁移检查点及兼容锚点的闭包之后，才发布新运行时、继续正常 recover；半迁移可见停顿，不能自动回落成无监督模式。

### 7.2 终态与降级

- 历史 completed/stopped 目标保持可读，不因容量修复重开。faulted completed board 继续按既有规则要求 stop/re-plan，不能以迁移为旁路。
- 旧版本程序无法理解 v2，必须明确失败，不能静默忽略新记录或覆盖账本。
- 回滚安装不等于能用旧程序继续写 v2 会话。需要保留新版本读取能力，或在原会话只读留档后另开旧版会话；**本次不承诺向下转换**。
- 新格式写入前后均不编辑已经存在的历史条目。恢复试验使用独立会话副本，不在真实任务历史上试验。

## 8. 失败优先级与可观测性

| 优先级 | 情况                                              | 行为                                                                       |
| ------ | ------------------------------------------------- | -------------------------------------------------------------------------- |
| 1      | 自有记录损坏、冲突、缺失前驱、锚点/当前分支不一致 | `journalFault`，禁止任务推进和盲目 recover；提示具体记录与检查方向         |
| 2      | 未闭合 intent、迟到结果、结果持久化失败           | 可见中断/证据缺口；保留原有更强 hold，不自动重放，不使用缺口前证明作新验证 |
| 3      | preflight 撤销、真实人类门、运行中宿主/已有执行   | 保持既有控制优先级；存储成功不能解除它们                                   |
| 4      | 有效但旧版本/旧审查/其他目标的回执                | 明确拒绝该证明，需要重新验证，不把它当成缓存故障                           |
| 5      | 缓存未命中/达到缓存预算                           | 正常读取日志或淘汰缓存，不改变 Supervisor 状态                             |
| 6      | advisor 完整保护材料超限                          | 保持现有 64,000 字节可见拒绝，不提高上限                                   |

status 建议增加：累计回执数、缓存数量/字节及预算、账本健康、待核对捕获数、存储格式版本。只有缓存容量显示分母，不能再把“累计 501 条”展示成预算用尽。

状态读取不写检查点、不清缓存计数、不触发 RPC、模型调用或自动恢复。真正磁盘/SDK 写入失败的提示必须说清“工具未执行”或“工具可能已执行”，不能笼统要求用户重试。

## 10. 分阶段落地与依赖

本表保留冻结方案时的实施 DAG 和初始状态，实时进展只维护在验收记录。实施不修改当前会话的旧已完成任务看板。

```text
G0 合同/并行写集核对 → G1 新目标跨越 500 条 → G2 旧目标无损迁移 → G3 生命周期与资源验收
```

| 节点 | 可独立核验的结果                                       | 消费/产出                                                         | 主要写集                                     | 状态         |
| ---- | ------------------------------------------------------ | ----------------------------------------------------------------- | -------------------------------------------- | ------------ |
| G0   | 版本号、事件顺序、并行/嵌套 epoch 规则及写集无未决冲突 | 消费本方案与另一任务交接；产出 symbol-level implementation packet | 实施包文档，不写生产代码                     | 待审阅后启动 |
| G1   | 新目标超过 500 条且历史证据、故障闭包仍正确            | 消费 G0 合同；产出账本/检查点 Interface 和长目标 RED/GREEN 证据   | store、runtime、supervisor、events、聚焦测试 | 未开始       |
| G2   | 旧版 500 条未完成目标显式恢复后继续，终态不被重开      | 消费 G1 格式和读取 Interface；产出迁移/分支恢复证据               | 相同共享文件及兼容测试，单 writer 串行       | 未开始       |
| G3   | 缓存和状态可用、日志近线性增长、SDK/全套回归通过       | 消费 G1/G2 行为及证据；产出最终验收记录                           | config、flow、smoke、文档与必要整合          | 未开始       |

- G0→G1 是 **contract** 依赖；宿主 hook/嵌套行为尚需验证部分同时是 **evidence** 依赖。
- G1→G2 消费持久化/解析合同，且共享源码有 **write-conflict**，不能假装可同时写。
- G2→G3 是迁移与生命周期 **evidence** fan-in；缓存默认值的探索可只读准备，最终接受不能早于 G2。
- WIP：一个 implementation writer；不默认启动子代理、额外正式审查或 workflow。
- 若 G0 小样本发现 SDK 不能提供需要的闭包，先修订本方案，不把架构选择留给写代码的代理临场决定。

### 11.1 最小到完整的验证顺序

1. 先用十余次事件的代表样本验证同一真实代码路径、intent/result 顺序、输出、失败处理和版本不变量；不得用千条运行发现普通 import/Schema 错误。
2. 聚焦测试 RED/GREEN：先稳定复现旧 500 条故障，再验证新实现；故障注入覆盖真实 append/branch 闭包，不只用全局对象数组假装落盘。
3. 参数化旧格式/当前分支/身份/中断测试；使用临时会话，不改真实历史。
4. 资源样本 100 → 1000 → 5000 条，固定每条负载和绑定集；每一级记录时间、插件新增日志字节、缓存高水位与结果。若 100 条样本失败，不继续放大。
5. 当记录编码固定后，以 `bytes(2N) / bytes(N) <= 2.5`（排除一次性旧版锚点）作近线性增长门；时间报告实测，不捏造跨机器毫秒指标。全分支解析调用次数也需可核验，不能每条结果做一次完整历史扫描。
6. 聚焦 GREEN 后运行基线 `npm run check`；维持当前 90% 覆盖率阈值，不为迁移放宽。
7. Pi 1.1 开发 peers 与实际 Pi 1.2 宿主都验证：保留八个现有 SDK/faux 模式，增加长回执、旧目标迁移与 intent 中断场景。采用现有精确快照、无 package-local `node_modules` 的冷加载方法；测试 UI stub 不算真实 TUI 验收。
8. 最终只接受一个明确 commit 的实现、测试和冷加载结果；保留原始失败证据。提交/推送以及后续 npm 发布/安装按后续授权分别办理，不能把本方案当作批准。

建议新增聚焦测试文件 `src/__tests__/receipt-store.test.ts`，并扩充现有 supervised-evidence、supervisor-acceptance、supervisor-packet、config 和生命周期测试；不新建第二套测试框架。
