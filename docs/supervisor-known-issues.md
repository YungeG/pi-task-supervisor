### F-01：外部执行生命周期未闭环

等待阶段会核对执行器的 Session、Run ID、协议版本及子节点状态；`clear_execution` 却只检查输入与现有引用相等，随后删除字段。最终验收只要求任务没有 executionRef，没有核验持久化的终态确认。

**实测**：执行器先报告 running，Supervisor 进入等待；Main 经公开准入/执行/结果链清除引用后，没有再次查询执行器。RPC 请求始终只有最初的 `[ping, status]`。随后新鲜验证、done 和目标 accepted 均成功，执行器仍为 running。

**风险**：在外部任务仍可修改受验产物时，目标可能提前被接受。探针未启动真实写文件进程，不声称观察到了生产文件损坏。

**修复方向**：把解除引用变成可信执行器确认的状态转换，核对 Session、Run ID、终态及子节点，保留终态回执并纳入最终验收。未知状态保留阻塞；失败/取消等终态必须有明确处理路径，不能一律视为成功。保证范围是可信执行器协议，不是 OS 级绝对静止证明。

### F-02：最终审查故障无法局部重试

**实测**：任务全部合法 done、最终验证有效，`acceptanceError()` 在模拟最终 Advisor 503 前后均无错误，完成证据未变。但 recover 因看板 completed 被拒绝；即使 Advisor 恢复可用，也不会再次调用。

**风险**：只有审查失败，却被要求停止、重建目标并重新组织证据。它与 F-03 共用“完成后缺少审查恢复路径”的问题。

**修复方向**：区分任务执行完成与目标审查完成，允许在权限、目标/看板摘要、产物版本、回执新鲜度和外部执行闭合仍有效时只重试审查。不重放任务、授权或首次启动，不顺便重置预算。不能直接删除 completed 恢复限制，否则真正失效的验收也会被重新开放。

### F-03：证据准入与审查容量不一致

**实测**：一个最终任务绑定 16 份合法成功回执，每份输出 1600 个中文字符；仅输出已有 **76,800 UTF-8 字节**。公开 advance 成功、快照有效、确定性验收通过，数据包却超过 **64,000 字节**。Advisor 调用数为 0，目标 fault；recover 又被 completed 限制拒绝。

**风险**：合法数据可形成正常终审无法处理的完成态。当前行为是失败关闭，不是静默截断或伪造证据；缺陷在容量与恢复规则不闭合。

**修复方向**：保留账本/宿主原始记录，独立构造有界审查视图，包含宿主结果结构、回执 ID/hash、必要摘录和产物版本；需要时由宿主受限补给详情。当前 Advisor 没有工具，按需详情机制尚不存在。提交 done 前应复用同一视图构造检查。不能通过无标记截断、放宽容量门或假称完整审查来掩盖问题。

### F-04：拒绝建议时漏记用量

`assertBatchAdvice()` 在 `recordUsage()` 之前。

**实测**：模拟模型返回格式合法的 guide，返回用量为 17 tokens、0.25 cost，但当前事实要求 next_batch。模型调用一次，`reviews=1`，`tokens=0`、`cost=0`，随后 fault/review_failed。

**修复方向**：把已发生的调用消耗与建议是否采纳分开，按调用身份记录有效已知用量，避免重复计算；同时考虑解析拒绝和晚到响应的原调用归属。

**边界**：这是 Supervisor 账目的 token/cost 漏记，**不是调用次数预算被绕过**，也不能由此推断 SDK 独立账单为零。未知用量不能伪造成已知数值。

### S-01：停滞策略过窄

4 份不同的成功 edit 回执，任务始终 implementing，仍在 `stagnant=3` 时暂停。现有设计有意排除 generation 变化、状态问答及工具次数，防止刷进度；但也会误判合法长步骤。

建议引入宿主可核验、去重并绑定产物版本的里程碑、差异或测试结果变化，同时保留总预算和循环上限。不能把成功工具调用次数直接等同于进展。

### S-02：建议动作错误即故障

现有测试 `src/__tests__/supervisor-batch.test.ts:98` 明确要求 guide / next_batch 不符合宿主状态时立即故障。F-04 用例也确认只调用一次模型就进入 fault，没有受限纠正。

可评估一次有预算的建议纠正，或在真实前置门禁满足时由宿主生成确定性 next_batch。不能重解释 hold、越过人工 pause/stop 或增加业务权限。这是策略调整，不是删除校验。

### I-01：Code Mode 调用树尚未进入证据模型

**局部实测**：外层 codemode 已准入，内层 bash 验证成功时 pending=1，done 被拒绝。外层返回后 pending=0，但内层 epoch=2/eligible=false、外层 epoch=1/eligible=false，当前 epoch=3，仍没有可用于验收的新鲜证据。

这是含潜在变更子调用的**嵌套事件模型**复现，不是当前真实插件 only 模式的端到端认证，也不能概括所有 Code Mode 组合必然失败。

正式修改文档核对了 SDK 1.1.0：tool_call/tool_result 已有 parentToolCallId，嵌套调用经过相同 hooks；应先消费现有字段，不默认另造父子协议。当前局部探针不等于真实元数据/only 模式验收，后续仍需核实实际树、修改顺序、非工具效果及容器静止边界。不能把所有 Code Mode 一概标只读，也不能在父调用仍可能修改状态时提前释放证据。

### B-01：宿主回执不独立证明需求被覆盖

当前确定性验收检查任务全 done、无执行引用、最终任务依赖闭包、任务摘要绑定及成功/新鲜回执。它不独立解释某条命令是否真正验证了某个功能。

preflight 已有 acceptance 文本，不能说完全没有记录验收要求；但尚无可执行的：

`验收条件 → 检查项及预期 → 产物版本 → 宿主回执`

相关性和完整性仍依赖 Main 的计划与 Advisor 判断。建立映射也需要可信检查定义和预期，不能仅由模型给任意成功命令贴需求 ID。

## 此前自行发现的生命周期管理问题

完整源码依据、模式对照和验证限制见[生命周期管理观察](reviews/supervisor-lifecycle-observations-ef47ec5.md)。以下不是用户补充四项缺陷的另一份复现，也不把必要的权限保护本身描述成漏洞。

### L-01：缺少统一、清楚的显式 opt-in 生效边界

扩展加载即注册钩子；enabled 控制工具暴露和续跑，但生命周期准入本身不以 enabled / Supervisor 是否已停止作为统一开关。已有 GoalRun 处于 planning 或其他非 active/reviewing 阶段时，尚无执行 Supervisor 或已停止监督也可能拦非只读工具。生命周期拦截以已经建立或恢复出的目标上下文为前提；没有历史的新会话并不会因此自动运行 Advisor，也不能据此说从未进入目标管理的普通会话必然被拦。

问题在于扩展已加载、会话已启用、GoalRun 存在、监督已启动是不同状态，却缺少清楚的管理模式与生效范围说明。不能简单加 enabled=false 放行来绕过未决授权或未知执行。

### L-02：stop 不是明确的会话级退出管理

stop 保留 activation、GoalRun、授权与历史；命令集没有与 enable 对称的持久化 disable/detach。会话恢复后可以重新恢复 enabled=true，**但这不等于重新启动已 stopped 的 Supervisor**。若用户想退出整套任务管理，仅 stop 不保证移除生命周期门禁，宿主停用扩展又属于不同操作。

未来退出路径需要明确旧历史、未闭合执行、人工请求和授权义务如何保留；不能通过退出伪造许可、终态或清空风险。原使用说明 M-01 归入此项。

### L-03：legacy 与新 GoalRun 模式的相同命令行为不同

全新兼容会话的 supervise 可直接启用监督并派发 Main；带已结束历史时，同一命令可能转入归档、新目标只读规划、独立权限与首次启动流程。stop 后，兼容模式可能允许普通工具，新 GoalRun 的 stopped/completed phase 则仍可能拦非只读工具。

这是历史/兼容性驱动的分流，不能把某次 stop 后 Git 成功推广成所有模式都可退出。需要清楚展示当前模式和转换，而不是偷偷复用旧授权以统一体验。

### L-04：完成后交接与粗粒度工具分类增加重建成本

新聊天请求、换目录/worktree 不自动创建新目标，这是身份隔离策略。另一方面，Bash、未标记只读的 Code Mode 等按潜在变更处理，不先分析 Git diff 或子命令实际效果；通过通用工具做只读检查也可能使旧验收过期。后续独立小任务和另行授权的交付收尾，可能被要求进入完整的新目标流程。

对话中确曾出现 accepted 后的合并请求触发新目标提醒，随后用户 stop 并成功继续 Git。但当时加载修订和 legacy/scoped 模式没有核实，不能把全部运行现象直接归因于当前源码。该项记录完成后工作归属/交接策略，与 F-02 的最终审查故障、F-03 的容量问题分别处理，不重复统计为另一个 P2。

### 运行版本边界

Git 更新不证明运行中的扩展已经重新加载。以上 L 项未做新的生命周期模式矩阵端到端测试，也未执行停用或重载验证；不应声称当前进程必定加载了该提交。
