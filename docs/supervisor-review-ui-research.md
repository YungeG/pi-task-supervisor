# Supervisor 审核 UI 调研与布局建议

调研日期：2026-10-27。

状态：**仅调研和设计建议，未选型、未施工。** 未安装组件、修改 UI 源码、改变确认协议或操作运行中的会话。本文不是实现验收或实施批准。

## 结论先行

推荐以 **单列审核单＋分区完整材料＋稳定操作区** 作为默认方向：借鉴 Huh 的终端表单交互、GOV.UK 的审核汇总与确认后下一步、Terraform 的具体计划与版本核对。优先复用现有 Pi TUI，不先引入 Go 表单库或新 Web 审批系统。

这里借鉴的是交互模式，不是照搬这些工具的授权语义。一次集中确认仍须覆盖明确材料并留下可信记录，独立 Start 和真实结果验收继续分开。[现有设计约束](./supervisor-consolidated-approval-flow-design.md)

### 已查看的视觉参考

实际查看了 Huh 官方 [Charm 主题截图](https://stuff.charm.sh/huh/themes/charm-theme.png)与[默认主题截图](https://stuff.charm.sh/huh/themes/default-theme.png)。前者突出分组及焦点，后者展示单色也能表达焦点与选择状态。

建议借鉴其层次和焦点表达，而不是照搬粉紫配色。使用宿主主题的中性底色与少量强调色，风险同时配文字标记，不仅靠红／绿区分状态。查看官方静态图片不等于验证了当前 Pi、SSH 或无障碍环境的真实效果。

## 2. 现有实现不缺基本呈现能力，缺少统一的信息组织

本次核对的源码基线为 `0f8f5f83e01a9db1d1e2c4662046471797897ab0`：

- `src/human-ui.ts::questionView` 已通过现有自定义 TUI 呈现内容；`requestNativeAnswer` 另负责来源、会话、分支、取消及原始回应注册。外观不应替代这些可信条件。
- `src/human-decision-card.ts` 已有会话卡、双栏、材料浏览和原文核对，并显示草稿／未提交状态。因此不能把现状描述为“没有卡片或详情页”。
- 现有卡片暴露 A／C 模式、F2／F3／F4、原文核对和材料切换；摘要取前几项、正文按可用高度截取。这些能力可以复用，但不必让用户先理解内部模式才能决定。
- `src/human-presentation.ts::preflightMaterial` 已有按权限和主题分区的材料；而 `src/acceptance-runtime.ts::reviewAcceptanceContract` 和 `verifyManualCheck` 仍把 `JSON.stringify(subject, null, 2)` 放入审核正文。不同请求的信息组织不一致。
- `src/human-scope-view.ts` 仍承担完整原文核对；当前流程不能只为减少步骤就移除该核对约束。

以上是源码观察，不是对正在运行界面的截图审计。仅据此不能判断用户终端的实际配色、字体和刷新效果。

## 3. 推荐布局：一个审核流程，不是强塞一个屏幕

### 3.1 默认单列审核单

按以下顺序组织，不默认把终端分成多个狭窄面板：

1. **标题和状态**：要决定的具体问题；尚未批准／已记录／尚未启动等状态明确区分。
2. **简短总览**：当前事实、为什么要决定、推荐及其依据、重要未知。
3. **范围和权限**：必需、可选、已有授权、本次未授权分开；选择只是草稿，不产生权利。
4. **验收要求与定义状态**：哪些本次确认、哪些检查器尚待形成；不把定义确认显示为结果通过。
5. **关键限制与风险**：对象、环境、写入范围、费用／限额、禁止事项、拒绝和部分批准的后果。
6. **完整材料及技术详情**：按主题浏览，不需要先读原始 JSON 才能找到主要边界。
7. **稳定的操作区**：准确的动作名称、当前焦点及按键说明；提交影响始终清楚。

“一次集中审批”指一次明确确认当前材料，不代表只能显示一个终端屏。长材料可分区滚动或分页，确认前必须可完整核对关键内容，不能为了美观截掉授权条件。[R1][R2]

### 3.2 低保真文字草图

以下只是布局示意，不是完整审批包、当前业务申请或已经实现的按键行为；实际对象、路径、限额和检查定义必须从同版材料填入并完整提供。

```text
审核本次方案                         尚未批准 · 尚未启动

需要你决定
是否批准本次所选权限，并确认列出的验收定义？

当前情况与建议
<已核实事实、未知事项、建议及理由>

范围与权限
  已有授权  <仍适用的权限，只展示，不重复申请>
  [ ] 必需  <动作、实际对象、作用范围与限额>
  [ ] 可选  <动作、影响与不选时的替代路线>

验收与边界
  <本次可确认的要求和检查定义；待冻结事项单独标明>
  <不会做什么、主要风险、费用和真实数据影响>

[查看完整材料]  [请求调整]  [暂不确认]
[批准所选权限与验收定义]

此确认只保存决定；通过其余就绪检查后仍需独立 Start。
按键提示依宿主绑定显示；默认焦点不应造成意外批准。
```

“暂不确认”与“明确拒绝”不是同一操作，不能用一个含糊的 Cancel 同时承担延期、拒绝或撤销。打开详情、修改草稿或调整窗口尺寸均不能产生批准；请求调整方案也不能悄悄替换已批准版本。

### 3.3 确认后立即给出下一步

成功、部分批准、原始事实已保存但投影待修复、写入结果未知，必须给不同反馈。只有完整可信保存后，才显示对应成功状态。

正常反馈应表达：确认记录已保存，尚未启动；系统先检查剩余就绪条件，满足后才提供独立 Start。未就绪时列明阻塞、处理人和合法动作，不用通用“继续”掩盖实际状态。[R3]

### 3.4 宽屏和浏览器是辅助，不是必经路径

- 宽屏可选“摘要／选项＋材料详情”双栏；默认路径不要求用户记住多个模式名和功能键。
- 窄 SSH 窗口优先单列、换行和滚动；状态与操作区尽量稳定，不能只能通过放大窗口才看见重要风险。
- 特别长的文档可提供 Markdown 或自包含 HTML 只读副本，并给 SSH 下载／本地转发方法；浏览器不能成为使用监督器的必需条件。
- 本轮不增加浏览器批准入口。复制页面上的按钮状态、stdout、退出码或“已阅读”标记均不是原生批准证明。

## 4. 外观改善不能削弱确认语义

- 用户视图和规范化材料须对应同一对象与版本；完整视图应保留实际权限、路径、限制、未知项和变更，而非自由摘要替代权威内容。[R4][R6]
- GOV.UK 的“修改后返回汇总”可借鉴为保留草稿和减少重复导航，不能据此把旧批准迁移到实质变化后的新方案。[R2]
- 不把 Enter 同时当“翻页”和无提示的“批准”；以当前焦点和明确动作区区分阅读、草稿与最终提交。具体键位与宿主保留按键冲突须在实施前解决。
- 不为了漂亮去掉控制字符、双向文本、重要空白和路径的安全表达；显示换行不能改变实际授权值。
- 让结构化完整视图承担现有原文核对职责，需要验证语义完整、来源绑定和变化检测；不能先删原文核对门再补这些保证。
- 用户提交期间材料变更、切树、取消或执行上下文失效时仍拒绝过期确认；UI 不是另一个权威来源。

## 5. 为什么不直接换库

Huh／Gum 的视觉和交互值得参考，但本仓库是 TypeScript，已有原生 TUI、主题、材料视图和受信回应路径。直接加入 Go 外部进程并不能解决验收合同内容组织、共同版本绑定或半写恢复问题；其输出也不能直接变成原生批准。[R1][R7]

因此优先顺序是：**整理信息和交互 → 用现有 TUI 做静态稿／受控验证 → 只有出现明确能力缺口，才讨论依赖或新的呈现机制。** 这是一项建议，尚未批准具体选型。

## 6. 后续需要验证，而不是现在宣称可用

- 用同一份真实长材料比较旧版与单列稿，验证用户能否找到决定、范围、风险、拒绝影响及下一步；不能只用短示例评价。
- 覆盖中文与长路径、60×20／80×24／120×40 等终端尺寸、窗口变化和常用 SSH 环境。它们是拟验证场景，不是已通过的兼容承诺。
- 覆盖浅色、深色及单色显示；键盘焦点清楚，不仅依赖颜色；借鉴 Huh 可访问模式的降级思路，但批准仍必须满足受信入口条件。[R1]
- 验证完整关键材料可阅读、内容与原始材料一致、错误及未知状态不丢失、草稿和最终确认不会混淆。
- 对 UI 变更仍需验证取消、过期、半写、恢复、用户暂停、缺失必需权限和不重复批准／派发；样式测试不能代替控制与见证测试。

本轮实际完成的是官方资料检索、两张官方示例图片查看及现有源码的只读核对。未运行参考工具、未搭建原型、未进行用户测试、真实 TUI／SSH 或自动视觉验收；不存在据此安装 Huh／Gum 或改动信任协议的批准。
